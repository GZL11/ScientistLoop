# 前端 PRD：科研智能体信息架构（Project → Workspace → 文献）

> 版本：v1.0（2026-07-10）
> 范围：从 project 第一入口，到文件模型（workspace / 原始输入 / 文献库），到右栏文献栏与引用片段的整套前端信息架构。
> 基准：基于现有代码 `famou-scientist/famou_scientist/assets/web/src/app.tsx`（现状快照见 `docs/前端快照_20260710/`）。本 PRD 标明「现状 → 目标 → 为什么」。
> 写作原则：**每个决策都带推理链路**（为什么这么做、为什么不那么做），便于评审时质疑与回溯。

---

## 0. 一句话与核心心智

**Project 是第一入口；Project 里只有两种真实存储——Workspace（干活的文件）和文献库（引用的论文）；用户几乎不用想"东西加哪去"。**

给用户的一句话心智：
- **要处理的文件** → 进 Workspace（agent 在这跑）
- **要引用的论文** → 进文献库（读它、引它）
- 除此之外没有第三个仓库要记。

---

## 1. 背景与要解决的认知混乱

### 1.1 现状（代码里实际有的）
左栏并列三个仓库：**知识库**（收藏文献+上传文档）、**资产**（有 workspace 产物的对话）、**MoonLog**；右栏有**产物 / 文献** Tab；中栏是 workspace 文件预览。

### 1.2 问题
同一类东西（尤其文献）能出现在多个地方 → 用户产生**"我到底加到哪里去"**的认知负担：
- 文献既在"知识库"又在右栏"文献"
- "资产"和 workspace 产物边界模糊
- 用户上传的文件夹、session 产出的实验文件、AI 检索的论文——分别落哪，规则不清

### 1.3 目标
**把"仓库"数量压到最少、把"加哪去"的决策降到几乎为零**，同时不牺牲科研必需的能力（代码可跑、文献可引、原始数据可保护）。

## 2. 关键设计决策与推理链路

> 这一章是本 PRD 的核心。每条都是「结论 + 为什么这么做 + 为什么不那么做」。

### 决策 1：区分「工作态」与「资产态」——这是整个模型的地基

- **工作态**：workspace 里的代码/数据/中间产物。依赖 project 上下文（目录结构、依赖关系），拿出去没意义。
- **资产态**：有独立价值、想复用的东西（一份清洗好的数据集、训好的模型、一篇文献）。脱离 project 也有价值。
- **为什么这么分**：之前一直把两者混谈才导致"加哪去"的反复纠结。分开后，**工作态锁在 project，资产态可跨 project 流动**——所有归属问题都能用这条判据解。

### 决策 2：取消"知识库"作为独立实体

- **结论**：不再有并列的"知识库"仓库；"给 AI 参考的文档"就是 workspace 里的文件。
- **为什么**：多一个并列概念 = 多一份"加哪去"的纠结。"参考文档"和"工作文件"本质都是 workspace 里的文件，没必要物理分家。
- **为什么不保留**：曾想过用"读/写"切分（知识库=读、workspace=写），但**"读/写"是系统实现视角，不是用户心智**——用户不会想"这文件给 AI 读还是写"，且很多文件天然又读又写（数据集）。维度作废。
- **唯一例外**：文献。它不是普通"参考文档"（见决策 4）。

### 决策 3：取消"资产"独立面板；用户上传物用「原始输入」标记保护

- **结论**：不做"我上传的 vs AI 生成的"对称二分标签；只保留一个不对称概念——**「原始输入」**（用户 pin 住的源文件）。
- **为什么不做来源二分**：价值不对称。"我想找我传的原始数据"是真需求（怕被 AI 中间产物淹没）；"我想找 AI 生成的"几乎不成立（用户在对话里就看到了，会回对话找）。做成对称标签是浪费。
- **为什么保留「原始输入」**：科研里"原始数据神圣不可改"是刚需。pin 成原始输入的文件受保护，agent 改动前要授权。这比 ChatGPT 的"已上传/已生成"更简洁、更贴科研。

### 决策 4：文献单独一个轻库，理由不是"读/写"，是它是「另一物种」

- **结论**：文献库作为**账号级**的第二块存储（不是 project 内）。
- **为什么单独**：
  1. **引用对象，不是工作文件**：你不 edit 一篇 arxiv 论文，你读它、引它、cite 它。
  2. **天然跨 project**：同一篇经典论文，风阻项目和润滑油项目都可能引。锁在单个 project 里别扭。
  3. **检索维度不同**：文件按文件名/类型/时间找；文献按作者/年份/DOI/语义找。塞一起两种检索都别扭。
- **这是 Zotero 模型**：账号级个人文献库，每个 project 只记"引用了其中哪几篇"。
- **为什么账号级而非 project 内**：本产品文献是核心（Deep Research 型、大量引用、产出带引用报告），跨 project 复用文献是高频的，直接做账号级。

### 决策 5：文件与文献条目是两回事（解决"用户传的论文 vs AI 找的论文"矛盾）

- **矛盾**：用户上传的论文打了「原始输入」在 workspace；AI 深度研究找的论文也落 workspace——那文献到底进 workspace 还是文献库？
- **结论**：**分清「文件」和「文献条目」**。
  - 一篇论文的 **PDF 文件** 可以在 workspace（agent 要读、要 cite）
  - 它的 **文献条目**（作者/年份/DOI/摘要/引用片段）进**文献库**
  - 两者指向同一篇论文；文献库里能看到"它在哪个 project 被引用过"
- **于是**：用户传的、AI 找的，**在文献库里统一成"文献条目"**，来源只是条目上一个小标签（📥用户传 / 🔎AI找），不影响它们平等地作为"可引用文献"存在。

### 决策 6：跨 project 复用产物 = 显式、低频动作，MVP 不做

- **结论**：产物默认待在它诞生的 project（零决策）；跨 project 复用是显式的"复制/存为资产"动作，且 MVP 先不做。
- **为什么默认不流动**：99% 情况产物就该留在原 project。若每次产出都问"加到哪个 project"，就又回到"加哪去"的混乱。
- **为什么低频**：用户真想跨 project 带走的几乎都是"资产态"（数据集/模型/图），不是随便一个 log。天然只作用于少数成品。
- **为什么 MVP 不做**：为低频场景提前增加复杂度不划算。架构上别把 workspace 文件和 project 焊死（留导出/复制的口子），等真实反馈再做。

### 决策 7：Workspace 底层保留目录树，人视图可铺平（不照抄 ChatGPT 纯铺平）

- **结论**：workspace 底层是**真实目录树**（保结构、给 agent 跑）；给人的视图可以另做"铺平/认物"式浏览。
- **为什么不照抄 ChatGPT 铺平**：ChatGPT 敢铺平因其文件是孤立成品（图/PDF 互不依赖）。科研 workspace 是代码+数据+实验，有目录和依赖（`train.py` import `utils.py`、读 `data/`）——**铺平了 agent 就没法跑**。
- **可借鉴 ChatGPT 的**：①文件即入口（选中文件→开新对话）②按来源筛 ③脱离 session 也能找到文件（用户认物不认路径）。

### 决策 8：存储架构（云沙箱常驻 vs 按需拉起）不进本 PRD

- **结论**：PRD 只锚定能力假设——**"每个 project 有一块持久、可跑代码、有目录结构的 workspace"**；底层是常驻沙箱还是按需拉临时环境，是后端实现，用户无感知，不写进 PRD。
- **为什么**：这是工程选型，不影响任何前端逻辑。别让存储架构卡住产品设计。

## 3. 目标信息架构（前端要呈现的结构）

```
账号级
├── 📚 文献库（Zotero 式，跨 project 共享）
│    文献条目：title / authors / year / doi / abstract / 原文链接
│    + 每条记录「在哪些 project 被引用、引用了哪些片段」
│
└── 项目 Project[]（第一入口）
     └── 🗂 Workspace（本项目唯一的文件存储，真实目录树）
          ├── [原始输入] 用户 pin 的源文件/数据集（受保护，改前授权）
          ├── [工作文件] agent 读写的代码/数据/中间产物
          └── [产物] agent 生成的结果（图/表/论文/数据）
          人视图：目录树 ⇄ 铺平资料库（认物、文件即入口、按来源筛）
     └── 💬 Sessions[]（多对话，聊天历史隔离，都对着同一 workspace 干活）
```

## 4. 界面改动（现状 → 目标）

### 4.1 左栏
| 现状 | 目标 | 说明 |
| --- | --- | --- |
| 知识库 / 资产 / MoonLog 三个并列面板 | **项目列表**（第一入口）+ 会话列表 | 砍掉"知识库""资产"并列概念（决策 2、3） |
| 知识库含"收藏文献+上传文档" | 文献并入**账号级文献库**入口；上传文档进 workspace | 决策 2、4 |
| — | MoonLog 保留（它是知识摘要，非文件仓库，不冲突） | — |

### 4.2 中栏
- 保留 workspace 文件预览 / 文献大屏（`PaperFocus` 已实现，见 4.4）。
- 新增：workspace **目录树 ⇄ 铺平资料库** 视图切换（决策 7）。铺平视图支持"选中文件→从此开启新对话"。

### 4.3 右栏「本次科研」= 视图，不是第三个仓库（关键）
- **产物 Tab** = 本 session 在 workspace 里**新增/改动的文件**（对 workspace 的过滤镜头，不新存东西）。
- **文献 Tab** = 本 session **引用/检索到的文献**（下沉到账号级文献库的入口）。
- **为什么强调"是视图"**：这是消除"两层级重复存"的关键——用户永远只有 workspace + 文献库两个真地方，右栏只是"这次产生了啥"的镜头。

### 4.4 文献卡与文献大屏（重点：现状盘点 + 增量）

**现状（已实现，不用重造）：**
- `PaperFocus`（文献大屏）已支持：title、authors、year、**doi**、**abstract**、原文链接（新标签打开 ↗ / 大屏内嵌全文 ↘ / 新标签看 PDF ↗）。
- `LitCard`（右栏文献卡）已显示：title、authors（前3）、year、摘要（非紧凑版）、原文按钮、★收藏、深入解读。
- 数据结构里 doi/authors/year/abstract 字段**都已存在**。

**所以"要不要加 DOI/作者/年份/摘要"——不用加，已存在。** 只需决定右栏卡片露多少（可选：卡片补 DOI 角标）。

**真正的增量 —— 引用片段（Deep Research 引用可追溯）：**
- 现状：`snippet` 字段只用于左栏搜索预览；文献卡本身没有"这篇在本次研究里被引用的具体片段"。
- 新增 paper 对象字段：
  ```js
  p.citations = [
    {
      snippet: "GNN 在 DrivAer 数据集上达到 R²=0.94",   // 被引用的原文片段
      location: "§4.2 / p.7",                          // 出处（可选）
      supports: "本研究采用 GNN 作为风阻代理模型",      // 支撑了我们的哪个结论（可选）
      verified: true                                   // 是否通过 arc_verify_citation 核验
    }
  ]
  ```
- 前端呈现：
  - `LitCard` 底部新增「被引用 N 处」可展开区，展开列出各片段 + 核验状态徽标（✅已核验 / ⚠️未核验）。
  - `PaperFocus` 大屏内新增「本研究引用」小节，列出片段 + 出处 + 支撑的结论。
- **为什么做这个**：这是文献栏唯一真正缺失、且高价值的能力——把"这篇文献支撑了本次研究的哪句话、在原文哪里、核验没核验"落地。天然接上代码里已有的 `citation-faithfulness` skill 和 `arc_verify_citation` 工具。

### 4.5 来源标记
- 文献条目加一个小标签：**📥 用户上传 / 🔎 AI 检索**（决策 5）。仅作展示区分，不做筛选主路径。

## 5. 用户如何"加东西"（消除认知混乱的最终答案）

| 用户动作 | 东西去哪 | 要不要用户决策 |
| --- | --- | --- |
| 上传一整个数据集文件夹 | Workspace（可 pin 为原始输入） | 否，直接进 workspace |
| 上传一篇参考论文 | 文献库（同时 PDF 落 workspace 供 agent 读） | 否，是论文就进文献库 |
| session 产出实验文件/代码/图 | Workspace（agent 本来就在这跑，自动落） | 否，零决策 |
| AI 检索到论文 | 文献库（条目）+ 右栏"文献"视图 | 否；★收藏是"提升为长期资产"的可选动作 |
| 想把 A 项目的产物用到 B 项目 | 显式"复制到其他 project" | 是，但低频，MVP 不做 |

**判断从"读还是写"降级成一句话**：**"这是要引用的论文吗？是→文献库；不是→反正都在 workspace。"** 几乎不用想。

## 6. 范围与优先级

### P0（信息架构收敛 + 引用片段）
1. 左栏改为「项目列表 + 会话」，砍掉"知识库""资产"并列面板。
2. 右栏"产物/文献"明确为**视图**（过滤镜头），非独立仓库。
3. Workspace 支持「原始输入」pin + 改动授权。
4. **文献卡/大屏新增「引用片段」展示 + 核验状态**（对接 arc_verify_citation）。
5. 文献条目加来源标签（📥/🔎）。

### P1
6. 账号级文献库独立页（Zotero 式：跨 project、按作者/年份/DOI 检索、看"被哪些 project 引用"）。
7. Workspace 目录树 ⇄ 铺平资料库视图切换 + 文件即入口（选中文件开新对话）。

### 待办（本期不做）
- 跨 project 复用产物（决策 6，架构留口不焊死）。
- project 级配置 / 研究图(provenance) / 项目系统提示词。
- 存储架构选型（决策 8，工程侧）。

## 7. 衡量指标
- 用户"加东西"时的犹豫/撤销率（认知混乱是否下降）。
- 文献引用片段的展开率与核验通过率（引用可追溯是否被感知）。
- 项目内二次对话占比、单项目 workspace 文件增长（长程积累价值）。
- 文献★收藏率、跨 project 文献复用率（文献库账号级是否成立）。

### 附：与竞品的一句话对照
- **ChatGPT 资料库**：文件铺平成个人网盘、文件即入口、按来源/类型筛——借鉴其"人视图"，但科研底层必须保留目录树（否则 agent 跑不了）。
- **Zotero**：账号级文献库、每处只记引用——文献库直接采用此模型。
- **OpenScience / Biomni**：workspace 绑工作目录 + citation 核验——引用片段接其 citation-faithfulness 思路。
