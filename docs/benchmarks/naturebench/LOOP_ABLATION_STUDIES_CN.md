## 一、跨任务经验库（cross-task ExpBank）

### 1.1 机制（当前做法）

每个 run 结束时由复盘 Agent 写一篇 Markdown 演化总结，upsert 进项目级库
`.famou/cross_task_expbank/`，按 NatureBench 官方六领域归档。下一个 run 启动前，
把库快照进 run 目录，并按**任务过滤方向**裁剪。

库是两层结构，这个形态本身就是 Idea Agent 的检索面：

```
<cross_task_expbank_dir>/
  index.jsonl        全部条目清单，一行一条 JSON
  protein_biology/   六个官方领域各一个目录
    <task_id>--<run_id>.md    一篇演化总结（一次完整 Run 的复盘）
  cellular_omics/ …
```

索引每行的字段：`domain` / `task_summary`（那道题在做什么）/ `result`（公开成绩
档位）/ `best_score` / `evolution_summary`（演化摘要）/ `summary_path`。Idea Agent
按自己的 domain 过滤索引（当前最大领域 21 行 16.3 KB），再打开相关条目的 Markdown。

- 代码：`famou_scientist/loop/storage/cross_task_expbank.py`、
  `famou_scientist/loop/examples/naturebench/fmjob/sync_cross_task_expbank.py`
- 开关：`CROSS_TASK_EXPBANK=1|0`、`CROSS_TASK_EXPBANK_SCOPE=cross|self`、
  `IDEA_PROMPT_VERSION`

**（1）任务过滤是双向的，两个方向互斥**

| `SCOPE` | 过滤参数 | 快照里留下的 | 用途 |
| --- | --- | --- | --- |
| `cross`（默认） | `--exclude-task-id` | 除本任务外的全部历史 | 跨任务迁移，即 1.4 那轮 |
| `self` | `--only-task-id` | **只有本任务自己的历史** | 同任务自身经验（1.8，未跑） |

两个方向都物理删除被排除条目的 `.md`，不只改索引——否则 Agent 可以绕过索引
直接 `ls` 目录。`seed_run` 末尾按方向选断言：`_assert_task_excluded` 或
`_assert_only_task_included`。**前者在参数为空时静默返回**，指望它兜底等于没有
断言，所以反向那条是新写的（`sync_cross_task_expbank.py:231/302/373`、
`submit_one_click.sh:131,307-311`），manifest 新增 `included_task_id`。

**（2）提示词已到 v6，且 v6 与 v5 的语义是反的**

v5 讲清了两层结构与检索方式，`cross_task_expbank_dir` 的定义是「**别的任务**的
经验」；v6 为 `SCOPE=self` 而写，把同一个占位符整个反转成「**本任务自己**的历史」，
连带翻掉三处反向指令（「按 domain 过滤索引」「必须论证可迁移性」等）。

> ⚠️ **`IDEA_PROMPT_VERSION` 默认仍是 `v1`，且与 `SCOPE` 之间没有任何交叉校验。**
> `SCOPE=self` 配 v5、或 `SCOPE=cross` 配 v6，都不会报错，只会让 Agent 拿着
> 一份描述反了的说明书去读一个方向对的库。跑任何一轮之前必须手动核对这对参数。
> （`cli_agent_wrapper.py:641-651`）

**（3）内容闸门的真实形态是「两处共用 + 一处手抄」**

文档此前写「在写入、重建、分发三个关口同步」。实际只有前两处共用函数：

| 关口 | 实现 | 判据 |
| --- | --- | --- |
| 写入 `upsert_summary:407` | 调 `is_agent_visible` | 合规通过 AND 有正文 AND 非离线补写 |
| 重建 `rebuild_catalog:494` | 调 `is_agent_visible` | 同上 |
| 分发 `seed_run:358-368` | **内联手写副本** | 同上 **＋ `judge_model` 过滤**，且 verdict **只认字符串 `"valid"`** |

分发侧严格更窄：`_is_judge_valid` 接受布尔与 Mapping 两种形态，这份副本不接受，
靠 `merge_outboxes` 预先归一才没炸。三处一致靠一条注释加一条单测
（`test_cross_task_visibility.py:323`）维系，**不是靠共用函数**——这是已知的残余
脆弱性，改任何一处都要手动同步另外两处。

**（4）提交路径恒带 `--skip-merge`，库不会在提交时增长**

40 个并发提交会在 NFS 记录锁上排队（实测 39 个进程卡在 `nfs4_retry_setlk`），
所以 `submit_one_click.sh:239-245,300-305` 默认跳过合并。合并需显式跑
`sync_cross_task_expbank.py`，或设 `CROSS_TASK_MERGE_ON_SUBMIT=1`。
**「库什么时候长大」由此变成一个人工动作**，做 A/B 时反而是好事（1.4 用的是
冻结快照），但日常跑批时要记得补合并。

**（5）「空但结构完好的库」的准确含义**

`CROSS_TASK_EXPBANK=0` 时只建根目录 + `README.md` + 空 `index.jsonl`，
**不建六个领域子目录**（`sync:312-327`）。「结构完好」指的是两条臂走同一段代码、
快照落在同一位置、载荷字段一致，不是指目录树长得一样。

**（6）剂量留痕随过滤方向切换**

收尾时 `run_summary.json → cross_task_expbank` 记 `entries` / `by_domain`；
`included_task_id` 不存在时记 `same_domain_entries`（`low_dose` 阈值 < 3），
存在时改记 `same_task_entries`（阈值降为 **< 2**）。（`harness/runtime.py:862-877`）

> **2026-09-09 前的形态不是这样**：调度器用 `CrossTaskExpBank.search()` 替 Agent
> 预选「同领域最多 20 条」塞进 `experience[]` 载荷，Agent 拿不到目录路径。那个
> 窗口是第一轮 A/B 失效的直接原因（1.2），已删除。

### 1.2 第一轮（20260906）：为什么这批数据不该用来回答原问题

15 题各跑一次 w/ 和一次 w/o，13 对可比。读数是**首次有效评测分**之差。

```
改善 7 / 变差 6      中位 +0.0068   均值 −0.0046   σ = 0.2275
```

7:6，中位贴零，测不出效应——但**问题出在剂量，不在效应**。跑的时候库里 141 条
目录条目只有 44 条有 Agent 手写正文，含 `When to use` 的仅 14 条（9.9%）；按当时
`search()` 的「同领域 → 按 `updated_at` 倒序 → 取 20」，**cellular_omics 那 4 个
任务窗口内有正文的条目是 0 条，处理臂严格等于对照臂**。

Agent 不是没读，是读到的没内容：224 次调用触库 222 次、累计 1189 次 Read、
去重打开 148 个 `.md`，其中有手写正文的 12 个（8.1%）；**20 个 w/ 臂 run 里打开过
跨任务 `index.jsonl` 的是 0 个**——v1–v4 提示词把 `expbank_dir`（本任务的库）
描述成跨任务快照、还让读一个并不存在的 `INDEX.md`，Agent 想自己检索也找不到门。

所以这一轮的正确表述是：

> 它证明「给 Agent 看一堆别的任务的方法名和分数」无效。
> 它**不回答**「真正的跨任务经验有没有用」。

这个阴性对照本身有价值：排除了「光靠罗列他题方法名就能迁移」这条路。

**σ = 0.2275** 是这 13 个 Δ 的总体标准差（`−0.6496 +0.2482 +0.0068 +0.1571
−0.0241 −0.0770 +0.3594 −0.1335 +0.0160 +0.0144 −0.0322 −0.0374 +0.0918`）。
均值几乎是 0，但单题 Δ 能跳到 ±0.65——**同一道题跑两次、配置完全一样，分数也能
差 0.2 上下**。它含三层随机性：① 两臂各自产方案，提的根本不是同一批 ② 同一方案
实现两次的差异 ③ 评测/环境噪声。所以**称它「实现方差」是错的**，应称 **run 间
方差**；三层里哪层是大头见 3.6。事前用辩论实验的 σ=0.119 估过功效，**实测估小了
近一倍**。

批次：`.famou/naturebench-submit-batches/20260906-xtask-expbank-ab-15/`

### 1.3 由此修掉的缺陷

诊断按「库 → 目录 → 下发 → 提示词」四段查了一遍，每段都有问题。

**（a）目录的过滤器与质量正交、且效果是反的**（2026-09-07 修）

```python
"agent_visible": _is_judge_valid(record)     # 只看合规判定，不看内容
```

后果：**90 条兜底垃圾在目录里，39 条 Agent 手写的好总结被挡在外面**
（其中 35 条只是 `judge_verdict` 为 `None`——从没判过，不是判为违规）。

修法是加一道**正交的内容闸门**，`is_agent_visible = 合规通过 AND 有
evolution_markdown AND 非离线补写`（三个关口的真实同步形态见 1.1(3)）。
配合补判 35 条（32 Valid / 3 Invalid）后：

```
改前   107 条目录，17 条有内容（16%）
改后    58 条目录，58 条全部有内容（100%）
```

**（b）目录条目本身无法区分**（2026-09-09 修）

Idea Agent 拿到的 20 条经验实测长这样：

```json
{"domain": "protein_biology", "result": "stopped", "best_score": 0.0904,
 "task_summary": null, "summary_path": "/.../s41467-....md"}
```

20 行只有一个浮点数不同。三个字段各自的原因：

| 字段 | 问题 | 修法 |
| --- | --- | --- |
| `result` | 存的是 Loop 生命周期状态，跑满墙钟一律 `stopped`，58/58 全同 | 投影时按 `best_score` 派生成绩档位；`achievement_level` 为唯一口径，生命周期状态挪到系统层 `run_status` |
| `task_summary` | 投影和载荷一直保留该字段，但 Loop 侧**从来没有人写**，只有离线补写脚本会填、而那批又被内容闸门排除 → 永远 `null` | 从公开题面（`problem/README.md` 标题 + 「Task Objective」段）写入；存量 198 条用 `backfill_task_summary.py` 回填 |
| `evolution_summary` | 目录里一直有，**下发时被投影丢掉** | 目录条目为唯一事实源，Agent 直接读索引 |

修后 58/58 三个字段齐全。

**（c）`search()` 预选整个删掉**（2026-09-09）

它做三件事，只有一件不能交给 Agent，而那一件恰好不在它里面：

| 它做的 | 能不能交给 Agent |
| --- | --- |
| 按领域过滤 | 能——库按六领域分目录，Agent 从题面就知道自己的 domain |
| 排序 + 截断 20 条 | 该由 Agent 挑，而这正是 1.2 里出错的地方 |
| 排除本任务自己的经验 | **不能**，但这是 `seed_run` 做的（删索引条目 + 物理删 `.md`） |

现在载荷只给 `cross_task_expbank_dir`，Agent 按 domain grep 索引后自行取用。
提示词出 v5 把两层结构、检索方式、`result` 的新口径讲清（v1–v4 逐字保留，
否则历史批次无法复现）。**其后又分化出语义相反的 v6，见 1.1(2) 的错配风险。**

**（d）一个让库自 09-07 起停止增长的回归**（2026-09-09 修）

09-07 把复盘产物从结构化 JSON 改成只留 Markdown 时，删掉了 `_summary_format`
辅助函数，却漏下一处**不带下划线**的引用：

```python
if args.role == "experience_summary" and summary_format == "markdown":   # NameError
```

它不是启动即失败，而是跑到收尾那一刻才炸：Agent 已经写完 `EVOLUTION.md`，
wrapper 在读它之前 `NameError`。**所以 09-07 之后每个 run 的复盘都没能回流**，
经验库从那天起不再增长——09-07 两个 verify run 的 outbox 里 `evolution_markdown`
都是 0 字符。当时只验了读侧（快照 58 条全有内容、Agent 打开了 5–6 篇），
没验写侧。

回归测试补在 `test_experience_summary_payload.py`：原有那条只查
`_summary_format`（带下划线），漏下来的标识符正好从缝里过去。

**（e）离线脚本的档位分支缺一格**（2026-09-09 修）

```python
result_label = "surpass_sota" if best_score > 0.1 else "match_sota"   # 没有 below_sota
```

只要 ≤0.1 就一律标 `match_sota`。**现存数据里 0 条被误标**（那 34 条 offline 记录
的 `best_score` 全在 0.0024–1.3353），是个潜在 bug；已归一到 `achievement_level`。

**（f）剂量从此有留痕**（2026-09-09）

这次的问题本可以在开跑前发现，但当时没有任何一处记着剂量，只能事后翻 220 个
agent trajectory 才算出来。现在两处留痕：

- seed 时写 `shared_experience_pool/cross_task_expbank_seed_manifest.json`
  （发了多少条、按领域各多少、排除/保留了哪个任务、从哪份库 seed）；放在快照目录**外**
- 收尾时 `run_summary.json` 的 `cross_task_expbank` 记 `entries` / `by_domain` /
  `same_domain_entries` 或 `same_task_entries` / `low_dose`（阈值见 1.1(6)）

**（g）补库**（2026-09-09 完成）

系统层有 127 条「合规通过但缺 Agent 手写总结」的记录，覆盖 82 个不同任务，
run 目录全部还在盘上。它们当年的复盘失败原因是 `missing agent result JSON`，
`worktree/EVOLUTION.md` 全是 21 字节的空壳，只能重跑。`resummarize_run.py` 真起
一个复盘 Agent（走 Loop 收尾那条通路、同一份提示词），因此不打 `offline_generated`，
只记 `resummarized` 做溯源。

补完后库从 **58 条 / 25 个任务** 变成 **192 条 / 83 个任务**。这 192 条就是第二轮
的冻结输入。

- 闸门测试：`famou_scientist/loop/tests/test_cross_task_visibility.py`（24 项）
- 载荷/目录/形态测试：`famou_scientist/loop/tests/test_cross_task_payload.py`
- 补判脚本：`.famou/naturebench-judge-reruns/run_expbank_content_rejudge.py`

### 1.6 第二轮：机制分析

分数是 null，但**机制链路逐段都通**——这是这轮比第一轮有信息量的地方。逐条标注
可复算性，**不可复算的不得当作有出处引用**。

| 段 | 数字 | 出处 | 可复算 |
|---|---|---|---|
| (a) 真的读了 | 触库 767 / 771 次调用 = **99.5%**；读 `.md` 634 / 771 = **82.2%**；60 个 w/ 臂 run **0 个**从未打开；每 run 中位打开 **6** 个不同条目 | `audit/readlog.txt`、`readfiles.jsonl` | ✅ 已复算 |
| (b) 真的进了方法字段 | 安慰剂对照净迁移中位 **+19.0**，**57 / 1 / 2**，p=4.09e-16 | `audit/transfer2.json` key `M` | ⚠️ 数组在，**口径不在** |
| (c) 引入了对照臂没有的技术 | leave-self-out **18% (11/60) vs 0% (0/60)**；NNLS 37% vs 10%；OOF 57% vs 30% | 仅 transcript | ❌ 未落盘 |

| (e) 剂量-响应全平 | Spearman ρ(净迁移词数, Δ) = **+0.088**，分层后每档 Δ 中位≈0 | 仅 transcript | ❌ 未落盘 |

> ⚠️ **(a) 的两个百分比是速率，不是比例。** `readlog.txt` 只统计到 run 粒度
> （每行 `<run_id> {"branches": n, "read_md": m, …}`），634/771 的含义是「每 100 次
> idea agent 调用发生 82.2 次 `.md` 读取」，**推不出「82.2% 的调用打开过库」**——
> 一次调用读两篇、另一次一篇没读也是这个数。能直接下结论的是另外两个：触库率
> 99.5%，以及 60 个 run 里 0 个从未打开。要拿会话级比例得重新采集。

**四项必须标注为不可复算：**

1. `transfer2.json` 只存了两组 60 长度的整数数组，**词表、placebo 抽样次数、是否
   限同领域、随机种子全部未落盘**，「方法段 vs 论证段」的划分只有自然语言描述。
2. 同目录 `transfer.json` 是**更早更宽的一版口径**（净中位 +36.5，60/0/0），
   与 +19.0 不是同一个数，**别混用**。
3. 路径真实性重算得 **341/379 = 90.0%**，当时报的是 90.7%，原始口径不可考——
   本文档用 90.0% 并注明算法。
4. `BEHAVIOR_DIAGNOSIS.md` 的 12 项行为指标底层数据与脚本同样未落盘，未独立复算。

**12 项行为指标**（60 对 / 1908 条 attempt，探索性，Bonferroni 阈值
0.05/12 = 0.0042）：唯一越过名义 0.05 的是**工程失败率 0.017 vs 0.091**
（14/29，p=0.032，绝对数 78 vs 119）——**没过 Bonferroni**，且**没有传导下去**：
产出率 p=0.272，最终分数 p=0.581。

合起来是一句相当窄的结论：

> 经验库不改变 agent **想什么**，只轻微改变它**能不能把想的东西跑完**，
> 而这点改变没有传导到产出率与最终分数。

这与 6.3 的判断一致：库里可迁移的内容几乎全是**工程与诊断能力**，而
`aggregate_improvement` 量的是**算法质量**。给的是工程能力，量的是算法质量。

### 1.7 复盘链路的一个取证 bug（2026-09-11 发现并修复）

排查第二轮时发现：**该批 105 份复盘里有 90 份是瞎写的**，正文写着「公开证据源
全部缺失」「没有 attempt 记录」之类。

**根因**（全仓唯一一处）：`build_experience_summary_prompt` 里写的是
`metadata = request`，而生产调用把 context 放在 `request["metadata"]`
（`agents/workers.py::summarize_experience` 传 `metadata=context`）。于是三个占位符
**同时**静默兜底：

```
goal/domain      → {}
expbank 路径     → 相对路径 "expbank"
attempt 目录     → 「没有 attempt 记录」
```

复盘 Agent 的 cwd 是 worktree，`ls expbank/` 必然扑空，于是它**如实**写下「证据
全部缺失」——这句话被当作正式经验存进库。2026-08 缺失率 2%，2026-09 升到 32%。

它能活一个月，是因为该文件此前**每一条用例都传扁平 dict**，恰好是生产永远不会
出现的形状。

**为什么这不影响第二轮的结论**：第二轮读的是 09-09 冻结的快照，而这批坏复盘产自
09-09 之后的这批 run 本身，**从没合并进那份冻结库**。冻结库 192 条发布条目按产出
模型拆：

| 产出模型 | 条目 | 占比 | 其中瞎写 |
|---|---:|---:|---:|
| opus | 70 | 36% | 3 |
| glm-5.3 | 64 | 33% | 0 |
| glm-5.2 | 30 | 16% | 2 |
| deepseek | 28 | 15% | 7 |
| **合计** | **192** | | **12（6%）** |

**即库的绝大部分是干净的，且不是自产自销**：实验本身跑的是 glm-5.3，读的是
以 opus 为最大单一来源、但三分之二来自其他模型的经验——「**别的模型写的经验 →
glm-5.3 读**」。这条链路成立，所以 1.6 的机制证据不因这个 bug 作废。

**修复与回归**：兜底值改成不可执行的标记（`未提供 expbank 路径`），而不是看起来
合法的相对路径；回归测试按**嵌套信封**断言（`test_experience_summary_payload.py`
的 `test_prompt_reads_the_nested_metadata_envelope` 等），并新增一条专门钉死
「三个兜底串一个都不许同时出现」。那 90 份坏复盘需用 `resummarize_run.py` 重生成，
**尚未做**。

### 1.8 结论与下一步

**结论：给 glm-5.3 看 83 个别的任务的真实复盘，在 14 道题上测不出分数效应
（8 正 5 负 1 平，p=0.581）。机制链路通，但效应止于工程失败率，没有传导到分数。**

这句话的边界要划清楚：

> 它说的是「**别人的**经验迁不过来」，**不是**「经验库这条路不通」。

三条约束同时成立，所以这轮的 null 不能外推：① 功效不够（需约 30 道有效题，实得
14）；② 缺失非随机，掉的两道全挂题恰是最脆弱的难题；③ 给的是工程能力，量的是
算法质量（6.3）。

**已评估但搁置：同任务自身经验 A/B（20260911）**

想法是把迁移距离缩到最短——快照里只放**这道题自己前几轮**的复盘，剂量最大、
匹配度最高。「若连自身经验都测不出来，问题就在复盘的产出质量或评测口径，不在
迁移距离。」设计已写完并落盘：

- `.famou/naturebench-submit-batches/20260911-selftask-expbank-ab-15x3/submit.sh`
  （15 题 × 3 重复 × 2 臂 = 90 个作业，`SCOPE=self` + 提示词 v6，复用同一份 09-09

- 同目录 `dispatch_parallel.sh`（一次铺开 30 个提交进程；同题两臂错开 20 秒，

## 二、多模型 Idea 辩论（idea debate）

### 2.1 机制

Idea 入队前先由一个**不同模型**的 Judge 批判（实验用 idea=glm-5.3、
judge=gpt-5.5，刻意不同模型以避免同模型的自我偏好）。Judge 读 in-task ExpBank
与跨任务库，按 7 项必答清单产出反馈；每条反对意见必须绑定可核查对象
（实例名 / 子指标名 / `expbank/00NN` / 跨任务 `summary_path`），绑不上的不许提。

两种模式：`respond`（Judge 只给反馈，作者自己决定改不改，保留作者权）与
`rewrite`（Judge 直接改写）。默认 respond、单轮。

双闸门激活：至少跑满 1 小时（兜底）**且**至少有 1 条 in-task 评测结果（主闸门，
否则 Judge 无据可批）。

- 代码：`famou_scientist/loop/agents/workers.py` 的 `_run_idea_debate`
- 提示词：`prompts/{benchmark_managed,cli_agents}/idea_judge.md`、`idea_agent_v4.md`
- 开关：`IDEA_DEBATE=0|1`（默认 0）

### 2.2 消融怎么做的

**任务内配对**：`emit_pair` 让同一次辩论同时产出「原版」和「改写版」两条 idea，
共享 `pair_id`、**优先级相同**、通过单调 `seq` 保证相邻消费。两条各自独立实现、
独立评测，因此同一任务内直接可比。

分数口径：**只取每条臂的首次评测**。refine 轮次在两条臂之间不对齐
（25 对里只有 13 对的 refine 轮数相同），比 refine 后的分数无法结构化对比。

批次：`.famou/naturebench-submit-batches/20260902-glm53-pair-5/` 等
文档：`docs/benchmarks/naturebench/IDEA_DEBATE_PAIRED_EXPERIMENT_CN.md`

### 2.3 结论

**25 对完成配对：**

```
全部 25 对        改善 12 / 变差 9 / 持平 4   中位 +0.0000   均值 −0.0373   σ 0.390
剔除单个离群点     改善 12 / 变差 8 / 持平 4   中位 +0.0023   均值 +0.0387   σ 0.119
```

**测不出效应**：效应 ±0.04 对 σ 0.119，需要约 70 对才能检出。

按原版分数分层（剔离群，24 对）：

| 原版起点             |  n | 改善/变差/持平 |            Δ 均值 |
| -------------------- | -: | -------------- | -----------------: |
| < −0.15（明显落后） | 19 | 11 / 5 / 3     |  **+0.0597** |
| ≥ 0（已达标）       |  4 | 1 / 2 / 1      | **−0.0512** |

### 2.4 过程质量好，但不转化

```
判官意见因缺证据被过滤       0 条（每条都绑定了实例名或 attempt 编号）
改写版的工程失败率           11%  vs  原版 15%
```

**判官在做真活、作者在改、改完更不容易崩——但都没换成分数。** 这才是最有信息量的
部分：瓶颈不在"idea 的论证够不够严密"这一环。

### 2.5 撤回过的两个说法

**① 「工程缺陷类批判有效、论证类批判有害」——否掉。** `metric_alignment` 这类
"论证性"批判的 Δ 均值是 −0.0019，看着有害；但**只要控制原版分数**（只看
origin < −0.15），同一批意见的均值翻正成 **+0.0266**。类型效应完全被起点效应解释掉。

**② 「已达标就不再改动」这条规律的独立佐证被削弱** —— 见第四节 4.4。

### 2.6 致命局限

原版与改写版是**两次独立实现**，Δ 里混着 run 间方差且无法分离。准确说法是
「**辩论的效应小于 run 间方差，测不出来**」，不是"已证明为零"。

> **本节此前写过"要补第三条臂测实现方差基线"——那条建议方向错了。**
> 实现方差后来在排序重放实验里顺带测出来了：同一条 idea 实现两次的绝对差值
> 中位只有 **0.017**，比 σ 0.119 小近一个数量级。混在 Δ 里的大头是
> **Idea 生成的多样性**，而那恰好就是 run 间方差本身，补 A/A 臂测不出新东西。
> 详见 5.2、5.3。

## 三、冲刺期 Idea 排序（time-aware idea ranking）

### 3.1 机制

剩余墙钟 ≤ 1 小时时，调一次 Judge 对**尚未实现**的 Idea 重排。Judge 按九个维度
逐项 1–5 打分（benchmark 对齐度、分数潜力、实现可行性、时间适配度、资源适配度、
证据支撑、互补性、后续改进空间、风险控制），**明确禁止固定权重求和**，
要求综合判断"在剩余时间和资源内产生更高正式分数的概率"。

排序结果翻译成队列优先级：

```python
item["priority"] = 2 - int(entry["rank"])    # rank1→1, rank2→0, rank3→−1
```

普通 Idea 默认优先级 1，所以它**只在新 Idea 之间重排，不会插到 repair/refine
（3/2 优先级）前面**。

三条设计约束（都是踩过坑写下的）：时间门控只触发一次；失败不自动重试；
少于 3 条待实现 Idea 不触发（一次 Judge 调用实测中位 270 秒）。

- 代码：`famou_scientist/loop/runtime/orchestrator.py` 的 `_maybe_rank_ideas` 段
- 提示词：`prompts/{benchmark_managed,cli_agents}/idea_rank_judge.md`
- 开关：`TIME_AWARE_IDEA_RANKING=1|0`（`harness/cli.py` 默认 False，**提交脚本把它打开了**）

### 3.2 为什么不能用观测数据直接评价

337 个触发过排序的 run 里：

```
deterministic_noop            142   队列 < 3 条，直接跳过（省了 Judge 调用）
ranked                        130   真调了 Judge
judge_failed_fifo_preserved    94   Judge 调用失败（42%）
```

但**被排序的 336 条 Idea 只有 13.1% 最终拿到分数**，「全部被排序的 Idea 都有分数」
的 run 132 个里只有 1 个。**被排在后面的那些根本没有分数，反事实不存在。**

也不能新建 run 重跑：**375/375（100%）的被排序 Idea 正文都引用了原 run 的具体
attempt 编号**（`基于 0004`、`relation=derived_from`），在全新工作区里
ImplementAgent 不知道 0004 是什么。

### 3.3 消融怎么做的：resume 原 run 重放

在原 run 里把**全部**被排序的 Idea 各重跑一次（含当时已实现的 rank 1），
同模型、同时并发、同样时间预算——**位置优势因此被彻底消掉**。

复用现成机制：`AsyncOrchestrator.run()` 启动时会调 `resume_task()`，它在
`termination_reason == "wall_time_budget_exhausted"` 时自动重排队、重置 actor、
清 shutdown，并把 `active_run_started_at` 重置为 now（墙钟预算完整重置）。
目标 run 中 129/132 正是这个终止原因。

配套关掉三样，各有理由：

| 关掉                          | 理由                                                                                                                                                      |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IDEA_GENERATION=0`         | 不关会继续产新 Idea，抢 implement 槽位并污染"只跑这几条"的比较。**不能用 `--iterations N` 代替**——它会把 `max_evaluator_submissions` 一起掐死 |
| `PAIRWISE_IMPROVE_SEARCH=0` | 实测 40.5% 的被排序 Idea 是被它当`offered_idea` 折进别的血缘而消失的                                                                                    |
| `MAX_IMPLEMENT_TURNS=1`     | 只测首次实现。允许 refine 的话 rank 1 会因先跑完而多得一轮，位置优势又回来                                                                                |

新增 `--idea-generation/--no-idea-generation`（`harness/cli.py`）与
`resume_run.py`（刷新 staged 源码、重建凭据、清 evaluator 通道标记、
复位 run 状态、幂等重放）。

批次：`.famou/naturebench-submit-batches/20260908-rank-replay-{3,8,10}/`
分析：`.famou/naturebench-judge-reruns/analyze_rank_concordance.py`

### 3.4 统计口径（预注册，在只有 4 对数据时固定）

**观测单位是 Run，不是 pair。** 同一个 Run 内的配对**因传递性不独立**：
rank1>rank2 且 rank2>rank3 时 rank1>rank3 自动成立。3 条 Idea 只有 6 种排列，
随机下"判对对数"的零分布是 `{0:1/6, 1:2/6, 2:2/6, 3:1/6}`，均值 1.5。

```
主指标  逐 Run 的判对对数，与该 Run 自身零分布比较；跨 Run 蒙特卡洛合并
次指标  top-1 准确率（Judge 排第 1 的实际分数是否最高）
规则    只取首次有效评测；无有效评测的不参与配对；分数并列的整对丢弃
```

早先说的"9 对、二项检验、需 8/9 才显著"是**错的**——那按独立配对算。

### 3.5 结论：无预测能力

**47 对配对、17 个可比 Run、15 个不同任务、6 个领域：**

```
一致率        53.2%（判对 25 / 判错 22，另 2 对并列丢弃）
主指标        P = 0.40（全部 Run）      P = 0.49（仅不重复任务）
次指标 top-1  7/16 = 44%
```

**和抛硬币无法区分。** 47 对在 80% 功效下能分辨 50% vs 64%，实测 53.2% 离下限还差
一半——**不是样本不够，是效应不存在或极小。**

### 3.6 副产品：同一条 idea 实现两次差多少（σ = 0.0798）

重放会把当时**已实现过**的 rank 1 idea 重新入队跑一遍，于是同一条 idea 有了两个分数：

```
原分数 = 原 run 里 lineage_id == 该 idea 的首次有效评测
重放分 = resume 之后 idea.replay_of_idea_id == 该 idea 的 attempt 的有效评测
d      = 重放分 − 原分数
```

9 对配对：

| run                    | rank |   原分数 |     重放 |                 d |
| ---------------------- | ---: | -------: | -------: | ----------------: |
| `s43588-024-00757-7` |    1 | −0.2870 | −0.2870 | **+0.0000** |
| `s41551-025-01528-z` |    1 |   0.0112 |   0.0119 |           +0.0006 |
| `s42256-022-00556-7` |    2 |   0.1964 |   0.1917 |          −0.0047 |
| `s42256-022-00556-7` |    1 |   0.1928 |   0.1979 |           +0.0051 |
| `s43588-024-00732-2` |    1 |   0.8272 |   0.8445 |           +0.0173 |
| `s43588-025-00917-3` |    2 |   0.2142 |   0.1714 |          −0.0428 |
| `s41592-025-02924-8` |    3 | −0.2141 | −0.1313 |           +0.0828 |
| `s42256-024-00916-5` |    1 | −0.4319 | −0.6438 |          −0.2119 |
| `s41592-025-02886-x` |    1 |  −50.62 |  −87.90 | **−37.28** |

⚠️ **最后一行是指标爆炸的题**（该题分数无尺度意义），单它就把总体标准差顶到
**11.71**——**直接对 9 对算 σ 会得到一个无意义的数**。剔除后的 8 对：

```
中位 +0.0003   均值 −0.0192   σ = 0.0798   绝对差中位 0.0112   最大绝对差 0.2119
```

**对比 1.2 的 run 间方差 σ 0.2275，相差 2.8 倍。** 所以 run 间方差里实现随机性
只占一小部分，**Idea 生成的多样性才是主要来源**。

两点使用注意：8 对样本本身不精确；最大绝对差到 0.2119，所以**单个配对 0.002 量级
的差异不可信**（这也是 3.5 只用计数型一致率、不用分数差的原因）。

### 3.7 「有没有用」要拆成两个问题

| 问题                   | 答案                     | 证据                                                                                                     |
| ---------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------- |
| 它有没有**作用** | **有**             | rank 1 拿到分数的概率是 rank 2 的**4.4 倍**（27% vs 6%）；rank 2 从未实现的概率是 rank 1 的 3.4 倍 |
| 它选得**对不对** | **不对，等于随机** | 47 对一致率 53.2%，P=0.40；top-1 44%                                                                     |

**它是一个真的杠杆，但拨动的方向是随机的。** 而它要花最后一小时里的
中位 270 秒、p90 570 秒。

### 3.8 「87% 跑不到」不是排序造成的

对比排序触发过 vs 因队列太短未排序的 run，看冲刺时刻仍待实现的 Idea 后来拿到
分数的比例：

```
noop（队列<3，未排序）    82 条待实现  →   2 条有分数    2.4%
ranked（调了 Judge）     129 条待实现 →  10 条有分数    7.8%
```

**两组都是绝大多数跑不到**，根因是容量约束：剩 1 小时、单次 implement 中位
26.6 分钟，队列里 3–5 条最多实现 1–2 条。排序只决定谁进那个名额。

（两组不可比——`noop` 组本来就是"队列<3"的 run，队列短往往因为整体产出慢、
剩余时间更紧。7.8% vs 2.4% 不能读成"排序提高了执行率"。）

### 3.9 建议与边界

**建议关闭**：`submit_one_click.sh` 的 `TIME_AWARE_IDEA_RANKING` 由 1 改 0。
关掉后走 FIFO——同样是任意顺序决定谁进名额，但不花那 270 秒。
**净效果为负**：作用真实、收益为零、成本非零。

一个未排除的替代解释：本实验给所有 Idea 都充足时间，**消掉了「哪条能在剩余时间
跑完」这个维度**。若 Judge 实际在优化完成率而非分数，关掉会有代价。
但提示词写的是「优先选择最可能**提升正式分数**的方案」，九维里 `time_fit`
只占一项。这个解释可以用现有数据测（rank 与"是否跑完"的相关），尚未做。

另一处观察：输出的信息量远大于实际用到的。九维评分 × 每条 Idea、
`reason`、`estimated_minutes`、`risks`、`summary`——**最终只有 `rank` 一个整数被
消费**，其余全部只落进 artifact 存档，无任何下游读取。

## 四、search-policy v2（pairwise improve）

### 4.1 机制

`evaluated` 续跑回合上，除了当前 refine 之外**同时租借一条排队中的新 Idea**
作为 `offered_idea`，让 ImplementAgent 三选一：

- `refine` → `replay_tail`，**Idea 保留**在队列里
- `switch` / `fuse` → `finish_lease`，**Idea 被消费**，折进另一条血缘
- 代码：`famou_scientist/loop/search/`（`PairwiseImproveSearchPolicy`）
- 开关：`PAIRWISE_IMPROVE_SEARCH=1|0`（默认 1）

### 4.2 ⚠️ 这一项**没有做过消融**

下面全是**观测数据**。观测不能回答"关掉会怎样"，因为选择是 Agent 自己做的，
与方案质量、剩余时间、队列深度全都缠在一起。**本节任何数字都不构成因果结论。**

### 4.3 观测到的三选一分布

| 批次              | 决策总数 |      fuse |    refine |   switch |
| ----------------- | -------: | --------: | --------: | -------: |
| opus-5（71 run）  |      329 | 155 (47%) | 151 (46%) |  23 (7%) |
| glm-5.3（58 run） |      279 | 113 (41%) | 112 (40%) | 54 (19%) |

glm-5.2 老批次 **0 条 `search_decision` 记录**——那时该字段还没写，无法比较。

### 4.4 父方案 = 当时最优时的选择与结果

「当时最优」定义为：做出该决策时（创建当前 attempt 之前）已知的全部有效分数中，
父 attempt 的分数最高。

| 批次    | 父=最优的决策数 |   refine |     fuse |            switch | refine 后改善率 |          delta 中位 |
| ------- | --------------: | -------: | -------: | ----------------: | --------------: | ------------------: |
| opus-5  |              50 | 26 (52%) | 24 (48%) |  **0 (0%)** |   53.8%（7/13） | **+0.000018** |
| glm-5.3 |              25 | 11 (44%) |  8 (32%) | **6 (24%)** |   54.5%（6/11） | **+0.000408** |

两个模型独立复现了同一形状：**父方案已是当时最优时，选 refine 的改善率
≈ 抛硬币（53.8% / 54.5%），delta 中位数几乎为零。**

**必须更正一处**：本记录此前多处写过「父=最优时选 switch 是 0/41 次」。
**该说法只在 opus-5 上成立**（0/50）；glm-5.3 下 switch 占 24%（6/25），
Agent 是会换路线的。凡引用"从不选 switch"的地方都应按模型限定。

### 4.5 这对第二节那条"唯一站得住的规律"的影响

辩论实验里我把「已达标就不再改动」称作唯一稳健的结论，理由是它有**两个独立
口径**支持：配对实验的 `origin ≥ 0` 分层（n=4，Δ 均值 −0.0512）与 search-policy
的「父=最优时 refine ≈ 抛硬币」。

4.4 的复算**支持后者**（53.8% / 54.5%、delta 中位 ≈ 0），所以这条规律的双口径
支撑仍然成立。但要注意两点：

- 配对实验那一侧 **n=4**，本身撑不住任何东西；
- search-policy 这一侧是**观测**，不是消融——它说明"在已达标方案上 refine 期望
  收益≈0"，不能说明"如果禁止在已达标方案上 refine 会更好"。

### 4.6 其他值得记的观测

- **40.5% 的被排序 Idea 是被这个机制消费掉的**（当 `offered_idea` 被 fuse/switch
  折进别的血缘）。冲刺期 Judge 花 270 秒排出一个顺序，然后四成排序对象被另一个
  机制直接消化——**两个机制在抢同一批 Idea，且没有协调**。
- 辩论配对实验丢掉的 16 条臂也是这个原因。第三节的重放实验因此必须把它关掉。

### 4.7 如果要做消融

关掉 policy 跑一批，**不比分数**（σ 0.22 的墙），比：

```
新 Idea 的产出/消费比        关掉后不再有 finish_lease 消耗
血缘多样性                   最终 best 的祖先数
被排序 Idea 的存活率         对第三节那个 40.5% 的直接检验
```

## 五、横向汇总：分数噪声这堵墙

### 5.1 两个方差数字

| 数值                  | 含义                                       | 算法在哪 | 样本  |
| --------------------- | ------------------------------------------ | -------- | ----- |
| **σ = 0.2275** | 同一任务**两次独立完整运行**的分数差 | 1.2      | 13 对 |
| **σ = 0.0798** | **同一条 idea 实现两次**的分数差     | 3.6      | 8 对  |

相差 2.8 倍——**run 间方差的大头是 Idea 生成的多样性，不是实现的不确定性。**

两者都是**同任务内**的配对差，不含跨任务方差。跨任务的分数量级差异极大
（从 +0.84 到 −499），这就是所有实验都必须用同任务配对、不能跨任务比较的原因。

### 5.2 对样本量的含义

```
任何 4h 单 run 口径下、效应小于 ±0.18 的改动，13 对样本都测不出来
要检出 ±0.05 的效应，需要约 165 对 ≈ 330 个 4h 作业
```

辩论实验（σ 0.119，效应 ±0.04）、经验库实验（σ 0.2275，效应 −0.005）都栽在这条线上。

**教训：这类实验开跑前先拿这个 σ 算功效。** 辩论实验没算；经验库实验算了但 σ
估小了一倍。

**经验库第二轮（1.5）换了个聚合方式绕这堵墙，没绕过去：** 改用「每题 3 次重复取
中位数定方向 + 跨题符号检验」，读的是符号不是幅度，本应对分数尺度免疫。结果是
**轮间残差 σ=0.1269 > 题间中位 σ=0.0873**——同一道题重复三次的抖动比题与题之间
的差异还大，于是「题级方向」本身就是个噪声量：16 道多轮题里三轮符号一致的只有
2 道（随机期望 8）。按实测的 0.688 正号比例，要压到 p<0.05 需约 30 道有效题，
而这类设计的作业预算上限就是 20 道。**换聚合口径解决不了样本量问题，只能换配对
粒度（5.4）。**

### 5.3 这个区分推翻了一条写过多次的建议

**「补 A/A 臂测实现方差基线」方向错了。** 辩论文档、经验库 README、提示词台账都写过
它。但实现方差已经由 3.6 测出（σ 0.0798），只占 run 间方差的一小部分。真正的大头是
Idea 生成方差——而那就是 σ 0.2275 本身，已经有了，补 A/A 臂测不出新东西。

四处均已加带日期的更正块。

### 5.4 绕开这堵墙的两条路

1. **换成计数/时间型的过程指标**——不受分数噪声支配。第三节的"一致率"就是这么
   做的（47 对二项检验），代价是回答的问题变窄了（保序性 ≠ 提分）。
2. **少任务多重复**——实测同一任务内方差远小于任务间：`s43588-024-00757-7`
   一个任务贡献 7 对时 Δ 全在 ±0.034 以内，而只有 1–2 对的任务动辄 ±0.15。

推到底，第 2 条的极端形式是**把配对做到 run 内**：同一个 run 里成对产出「用经验」
与「不用经验」两条 idea，其余全同（辩论实验的 `emit_pair` 就是这个结构）。

**它省的样本量要按 idea 级配对的 σ 算，不是按实现方差算。** 现成的实测标尺就是
辩论实验——同 run 内、同轮次、原版 vs 改写版，σ = 0.119（3.6 那个 σ 0.0798
是「同一条 idea 实现两次」，与此无关，别拿它估功效）：

```
run 级 A/B      σ 0.2275 → 检出 ±0.05 需约 165 对（≈330 个 4h 作业）
run 内 idea 配对 σ 0.119  → 检出 ±0.05 需约  44 对（≈15–18 个 run）
```

**但 run 内配对有个结构性限制：能干净测的只有早期几轮。** in-task ExpBank 会
累积「由读过库的 idea 产出的 attempt」，run 跑到中后期，读不到跨任务库的那条臂
也能从本任务经验里间接看到对侧的产物。所以它回答的是「此刻把库交给这条 idea
会不会改变它」，**不是**「一个 run 有库跑 4 小时会不会更好」。

绕法：**在第一条有效评测落地之前连发若干对**。那一刻 in-task ExpBank 还是空的，
两条臂状态完全相同，污染为零；而实测首条有效评测来得很晚（辩论实验里一半的 run
到最后 1.2 小时才有），窗口足够连发 2–4 对。这样每个 run 能拿到 2–4 对**干净**
配对，10 个 run 约 30 对，接近 44 的门槛。

中后期的配对仍然记录，但要**分层报告**（前 3 轮 vs 全量）：两层结论一致，说明
污染不主导；不一致，就只认前几轮那部分。

## 六、方法论上反复出现的五个陷阱

记下来是因为这几轮里**每一个都犯过至少两次**。

### 6.1 事后挑指标

经验库那批分数没信号后，我列了四个过程指标、砍掉一个算不了的，剩三个里两个
没信号，只报了第三个（"同一个坑连着撞" 5 vs 13）。**这是先射箭再画靶子。**

第三节因此改成**预注册**：主/次指标、零假设、判据全部在只有 4 对数据时写进批次
脚本注释，之后不改。

### 6.2 一个错误码盖多个病

```
missing agent result JSON   67 次 idea_rank 失败 + 99 次复盘失败，是两个不同的病
agent_api_error             8 次凭据问题（我引入的）+ 4 次上游 Bad Gateway
judge_error: HTTP 502       间歇性上游抖动，被误读成"端点配错"
```

`agent_api_error` 那两个病症状完全相同，第一次修完没变化，**得靠复现文件属性
（`mode=0600 uid=0`）才分清**。

### 6.3 用错误的指标量

经验库里可迁移的内容几乎全是**工程与诊断能力**（43/58 篇有工程/契约教训，
只有 6 条诊断启发），而 `aggregate_improvement` 是**算法质量指标**。
**给的是工程能力，量的是算法质量**——这是两轮都测不出效应的一个可能原因，
跟样本量关系不大。

### 6.4 只验了一半的链路，就当成"修好了"

09-07 修完内容闸门后跑了两个 verify run，结论记成「库已修好、端到端验证通过」。
实际验的只有**读侧**：快照 58 条全有内容、Agent 打开了 5–6 篇。**写侧同时是坏
的**——那两个 run 自己的复盘都以 `NameError` 收场，`evolution_markdown` 是 0 字符
（1.3d）。于是「修好了」的结论下面，库其实从那天起就不再增长。

经验库是个**闭环**：读（Agent 取用）+ 写（run 结束回流）+ 发布（合并进库）。
验证必须绕完整圈，任何一段只验一头都会得出反向结论。

### 6.5 静默降级比直接失败更危险

复盘 Agent 的取证入口错了一个月（1.7），没有任何一次抛异常、没有一行日志。
三个占位符**同时**兜底成看起来合理的值，其中最糟的是把 expbank 路径兜成相对路径
`expbank`——它像个合法挂载点，Agent 于是真的去 `ls`，在 worktree 下必然扑空，
然后**如实**写下「证据全部缺失」。那句话被当作正式经验存进库。

比留空更坏：留空会让 Agent 报「参数缺失」，一眼看出是配置问题；一条看似合理的
错路径把配置故障伪装成了数据故障。修法是把兜底值改成**不可执行的标记**
（`未提供 expbank 路径`）。

同一处失效模式这是第三次：`_summary_format` 的 `NameError` 跑到收尾才炸
（1.3d）、只验读侧就宣布修好（6.4）、这次的三重兜底。共同点都是**故障发生的
位置与被观察到的位置隔了很远**，而中间那段不出声。

1.2 的错误；第四条是第二轮之后新增的）：

1. **剂量前置检查**：seed 后看 `cross_task_expbank_seed_manifest.json` 的
   `by_domain`，同领域少于 3 条的任务不入组（也可以直接看 run 结束时的
   `run_summary.json → cross_task_expbank.low_dose`）。
2. **提示词版本必须与 `CROSS_TASK_EXPBANK_SCOPE` 对上**：`cross` 配 **v5**，

3. **验证阅读行为**：跑完从 trajectory 统计「打开了几篇 / 其中几篇与本任务同类」。

4. **分析口径连同脚本一起落盘**，不要只留会话里的临时 heredoc。第二轮的迁移、
