## 零、结论

1. **我们的 Judge 测不出排序能力**：pairwise 一致率 54.4%（57 对，random 50%），top-1 41.2%（random **36.5%**，因为平均每 Run 只有 3.0 条候选），主指标 P=0.32；去掉重复任务后 51%，P=0.4989。**按各自基线折算，pairwise 与 top-1 的提升都只有 +4~5pp，不算显著。**
2. **换成「真实收益」口径，方向偏正但仍不显著**：排序后第 1 名 vs 不排序时的第 1 名，16 个 Run 里 11 胜 5 负，Δ 中位 **+0.0057**，p=0.21。增益比噪声小近 40 倍。
3. **但这两条可能都问错了问题**：18 个 Run 里有 **12 个**的候选极差 ≤ 实现噪声 σ=0.0798。三分之二的 Run 里，那几条 idea 的可达分数本来就在噪声内，**序由噪声决定**。
4. **论文给了参照系**：同类任务（MLE-bench，1.8 万对）的 SOTA 一致率是 **61.5%**，且其增益主要来自一份我们完全没有的输入——**Verified Data Analysis Report**。
5. **最该改的不是 Judge 的判别力，是三件周边事**：允许并列、输出置信度、补数据报告。详见 §五。

## 一、我们测到了什么

实验本体（设计、为什么必须 resume 原 run、预注册口径）见消融文档 §三，此处不重复，只列与本文论证相关的读数。

### 1.1 预注册主指标：无预测能力

```
18 个可比 Run / 15 个不同任务 / 57 个可比配对（另有 2 对并列丢弃）
判对 31  判错 26   一致率 54.4%
```

> （rank1>rank2 且 rank2>rank3 时第三对自动成立），按 57 个独立 pair 算会高估显著性。
> 54.4% 只是描述性数字。

## 二、候选之间有没有梯度（这条比前面两条更关键）

### 2.1 为什么要问这个

Meta AIRA（[arXiv 2507.02554](https://arxiv.org/abs/2507.02554)，NeurIPS 2025）把 research agent 形式化成 `(F, π_sel, O, π_op, τ)`，然后报了一个阴性结果：

> **用 AIDE 原始算子集时，MCTS、进化算法相比贪心搜索没有任何收益——三者夺牌率
> 都在 35~39%。只有把算子换成 AIRA 版本之后，MCTS 才拉开到 47.7%。**

即：**选择策略 `π_sel` 的收益上限，被候选生成算子 `O` 的质量卡死。**

我们的 rank judge 正是一个 `π_sel`。所以在继续追问「Judge 准不准」之前，必须先确认候选侧有没有可供选择的真实差异。

### 2.2 噪声尺子用哪把

用 **σ = 0.0798**，即「同一条 idea 实现两次」的标准差（消融文档 3.6）。**不用** run 间的 σ = 0.2275——后者含「两臂各自产方案」的差异，而这里比较的正是不同方案，用它会把要测的信号也算进噪声。

### 2.3 实测：三分之二的 Run 里没有梯度

```
12 / 18 个 Run 的候选极差 ≤ σ = 0.0798      极差中位 0.0311
逐 Run 极差：37.4438  0.5442  0.5387  0.2874  0.2100  0.1101  0.0679  0.0364
              0.0320  0.0301  0.0146  0.0092  0.0081  0.0081  0.0081  0.0071
              0.0047  0.0022
```

**多数 Run 的全部候选挤在一个比实现噪声还窄的区间里。** 极差 0.0022~0.0092 那几个 Run，意味着无论 Judge 怎么排，最终分数都一样——序完全由抖动决定。

这也解释了消融文档 §三第三批注释里记的那两个「完整倒序」案例：
`s41551-025-01528-z` 的三条 idea 分别是 0.0119 / 0.0122 / 0.0140，**不是 Judge 判错，是这三条 idea 的可达分数几乎相同。**

### 2.4 「分差大则排序准」这个推论：测不了

第三批 `submit.sh` 里提出过一个可检验推论。按真实分差分桶：

| 桶             |  n | 判对 | 一致率 | 符号检验 p | 覆盖任务数 |
| -------------- | -: | ---: | -----: | ---------: | ---------: |
| < σ (0.0798)  | 39 |   23 |  59.0% |      0.337 |         12 |
| σ ~ 3σ       |  6 |    3 |  50.0% |      1.000 |          4 |
| > 3σ (0.2394) | 12 |    5 |  41.7% |      0.774 |          4 |

> ⚠️ **不要读这张表的趋势。** 三个桶 n 分别是 39 / 6 / 12，每桶 p 都在 0.3 以上；最大分差那桶的 12 对里有 **6 对来自单个指标爆炸题** `s41592-025-02886-x`，剔除后只剩 6 对（判对 2）。
>
> 诚实的表述是：**这批数据不足以检验该推论**，既不支持也不推翻。表面上呈现的「分差越大越不准」是样本噪声，不是发现。

## 三、论文对照

> **获取限制**：本节内容来自检索返回的摘要，**不是通读原文**所得。
> 本机环境对 arxiv.org / github.com / openreview.net 的直接抓取被域名校验拦截。带具体超参的数字（m=10、置信阈值 0.7、k=1）**必须对照原文核对后再用**。

### 3.1 [Can We Predict Before Executing Machine Learning Agents?](https://arxiv.org/abs/2601.05930)

ZJUNLP，ACL 2026（**注意是 2026-01，不是去年**）。代码：[zjunlp/predict-before-execute](https://github.com/zjunlp/predict-before-execute/)

与我们做的是**同一件事**：判断候选方案孰优孰劣，且不执行。

|          | 内容                                                                                                                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 任务形式 | Data-centric Solution Preference ——**pairwise**：给任务描述 + 数据报告 + 两个候选，判哪个更好**并给置信度**                                                                                                     |
| 语料     | 从 AIDE / AutoMind 在 MLE-bench 上的真实轨迹抽取，26 个任务、1329 个有效 solution、**18438 个 pairwise 比较**，胜者位置做过平衡以消除位置偏置                                                                           |
| 关键输入 | **Verified Data Analysis Report**：「Code-Execution-Verbalization」协议——真的跑代码算出统计量，再把原始统计量**转写成语义叙述**。论文明确说「只给代码是不够的」，模型是靠理解数据特性及其对模型设计的含义来推理 |
| 用法     | ForeAgent 的 Predict-then-Verify：并行提 ~10 个候选 → 置信度门控（阈值 ~0.7）的 pairwise 筛选 → 只有 top-k（k=1）真跑                                                                                                       |
| 自陈缺陷 | **全局 listwise 排序存在 scalability defect，全局判别力不足**                                                                                                                                                           |

**一致率对照：**

|                                     |          一致率 |
| ----------------------------------- | --------------: |
| DeepSeek-V3.2-Thinking + 数据报告   | **61.5%** |
| GPT-5.1 + 数据报告                  |           58.8% |
| 复杂度启发式                        |           50.8% |
| 随机                                |           50.0% |
| **我们（57 对，无数据报告）** | **54.4%** |

> ⚠️ **不要直接对比 61.5% 与 54.4%。** 三个不可比之处：
> ① 样本差三个数量级（18438 vs 57）；② 他们多了一份数据报告；
> ③ **他们的 fitness 是 5-fold CV 分数（有执行过的 proxy 信号），我们的冲刺期
> Judge 是纯预测、零反馈**——我们做的是更难的任务。

**结论层面的一致之处：两边都测出「弱到接近随机」**——他们的 pairwise 61.5% 对 随机 50%，我们 54.4% 对 50%、top-1 41.2% 对 36.5%。

> ⚠️ **不要把他们「listwise 全局排序垮掉」的结论套到我们头上。** 我们的 top-1 相对自己的基线提升 +4.7pp，与 pairwise 的 +4.4pp 基本持平（§1.1），**本批数据不支持「我们的定序比两两比较更差」**。而且我们每 Run 平均只有 3.0 条
> 候选，这个规模上 listwise 与 pairwise 本来就没有实质区别——他们说的 scalability defect 是候选数上去之后才显现的问题，我们还没走到那一步。

### 3.2 [AI Research Agents for Machine Learning](https://arxiv.org/abs/2507.02554)

Meta AIRA，2025-07，NeurIPS 2025。**这篇才是「去年」那篇**，但它研究的是搜索策略与算子，不含「执行前预测分数」这个指标。

- 形式化：`(F, π_sel, O, π_op, τ)`，算子含 Draft / Debug / Improve / Memory / Crossover
- 搜索策略：Greedy / MCTS / Evolutionary / AIDE-style
- SOTA：MLE-bench lite 夺牌率 39.6% → **47.7%**（AIRA_mcts）
- **对我们最有用的是 §2.1 引的那个阴性结果**，以及泛化缺口：按 test 分数选最终方案（oracle）能再提 9~13 个百分点，说明 validation→test 的噪声本身就吃掉了很大一块

## 四、差距分析：我们的 Judge 差在哪

对照 `famou_scientist/loop/prompts/cli_agents/idea_rank_judge.md`：

| #           | 论文做法                                              | 我们现在                                                                             | 影响                                                   |
| ----------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| **1** | Verified Data Analysis Report（跑代码 → 转写成叙述） | 只给公开任务描述、剩余墙钟、资源、正式排行榜、ExpBank 证据。**零数据特性信息** | 这是 61.5% 的主要来源；去掉就回落到启发式水平（50.8%） |
| **2** | Pairwise，且自承 listwise 是缺陷                      | 要求「严格全序」「**rank 不得并列**」                                          | 我们直接选了论文自己都做不好的形态                     |
| **3** | 输出置信度，低于阈值不采信                            | 输出 9 个 1–5 分维度 + rank，**无置信度**                                     | 这是把弱信号变成可用信号的关键机制                     |
| **4** | m≈10 候选并行提案后再筛                              | 冲刺期只有 2~5 条候选                                                                | 池子太浅，筛选没有发挥空间                             |
| **5** | fitness 含 5-fold CV（有执行反馈）                    | 纯预测，冲刺期无任何执行反馈                                                         | 我们的任务更难，不能直接对标 61.5%                     |

**第 2 条值得单独说：「不得并列」这条约束在我们自己的数据面前是有害的。**
当候选真实分差是 0.002、而实现噪声是 0.0798 时（§2.3 的 12 个 Run 就是这样），强制 Judge 给出全序 = 强迫它在噪声上编造顺序，然后我们再去考核这个编造出来的顺序。分析口径已经把「分数并列的配对整对丢弃」了，**但 Judge 那一侧没有对等的出口**。

与 [`IDEA_QUALITY_LITERATURE_CN.md`](IDEA_QUALITY_LITERATURE_CN.md) §2.4 的呼应：IdeaAgent 的自估收益也是同一个形态——跨任务有相关（ρ≈0.32~0.44），**run 内排序 Spearman 中位仅 0.255、55 个 run 里 23 个为负**。两个独立的排序机制（Agent 自估、Judge 排序）在同一个位置失效：**run 内部**。

## 五、改进项（按性价比）

### P0. 允许并列 + 输出置信度

改 `idea_rank_judge.md` 的协议与 schema：

- 去掉「rank 不得并列」，允许 Judge 声明「这几条我分不出来」
- 新增 `confidence`，以及判据说明（为什么有把握 / 为什么没有）

有了置信度才能做门控：**高置信按排序执行，低置信退回 FIFO。**这样即便判别力只有 54%，也不会亏——这正是 ForeAgent 让 61.5% 变得可用的机制。成本最低，且不需要新实验就能上。

### P1. 补 Verified Data Analysis Report

论文里增益最大的一块，而 NatureBench 每道题都有公开数据，我们完全有条件在 run 启动时跑一次数据分析、缓存、全 run 复用。**关键是照论文做法转写成叙述**，不能只丢统计量或代码。

### P2. 先查 IdeaSpark 的候选多样性，而不是继续调 Judge

§2.3 已经给出方向性证据（12/18 个 Run 无梯度），但那只是 18 个 resume Run。应当在**全量** ExpBank 上复核：同一 run 内候选 idea 的分数分布有多宽。若结论一致，则瓶颈在 IdeaSpark 的多样性，**Judge 这条线应当直接降优先级**。

### P3. 把冲刺期候选池做深（对应论文的 m≈10）

动了触发条件，等 P2 结论再说。

### 明确不做

- **不再用当前形态加样本重测排序**。池子已经用完（见 §六），而且在候选无梯度的前提下，加样本量测的是噪声。
