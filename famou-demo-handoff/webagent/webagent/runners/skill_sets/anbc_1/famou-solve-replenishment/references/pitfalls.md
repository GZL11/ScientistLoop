# 补货 / 采购常见坑 + 退出自检清单

> 本文件中的具体数字(如"5 DC × 3 SKU × 20 周 = 300 行"、"占比 ≤ 40%")
> 都是**典型样貌**,用于说明踩坑形态。**真正的约束以用户提供的问题描述为准**——
> 可能是 7 仓 4 SKU 12 期、占比上限 30%、其他字段名。读 pitfall 时关注**形态**而非具体数字。

## 通用坑

### 坑 0:库存守恒方程写错符号 / 漏项

最常见的 bug。建议在脚本里**先用注释把方程写出来**,每个 +/- 项都标注:

```python
# inv[t] = inv[t-1]
#        + arrival[t]              # 到货(提前期=0 即 order[t],否则 order[t-L])
#        - demand[t]
#        + short[t]                # 占位变量:未满足的需求(注意是 + 不是 -)
#        - waste[t]                # 损耗
#        + sub_in[t] - sub_out[t]  # 替代品双向(仅与 SKU 相关)
#        + transferred_in[t] - transferred_out[t]  # 调拨双向(Hub-Spoke)
```

再实现。**`short` 是加号不是减号**——它代表"未消耗的部分"。

### 坑 1:交付字段名/文件名/行数不匹配

若问题描述写"N DC × M SKU × T 期 = N×M×T 行(不含表头)",必须刚好匹配。
零下单的也要写出来(`order_qty=0`、`end_inventory` 计算正确)。
中英文字段名逐字保留。

### 坑 2:MILP "Optimal" 不等于建模正确

求解器在你写下的约束里最优。运行后**用独立验证**(另写一段函数 / 另写一脚本 / 不同实现思路)逐 `(dc, sku, t)` 验证守恒、容量、合同、占比。

### 坑 3:big-M 设置太大(数值不稳)

`big_M = 1e9` 在 CBC 里常导致 LP relaxation 数值漂浮。
合理值:`big_M = total_demand * 1.5` 或同量级常量。

### 坑 4:提前期引导期缺货——结构性成本 vs 建模错误

**现象**：初始库存为零且提前期 > 0 时，前 L 期必然出现缺货，验证函数报告缺货成本。

**根本原因**：这是由问题结构（初始库存=0 + 提前期约束）决定的**结构性成本**，不是建模 bug。若问题允许在第 1 期前预下单（pre-ordering），应在建模中显式支持；若不允许，该缺货成本是理论下界，不应试图通过修改约束来消除。

**正确做法**：

1. 在建模前**明确问题是否允许 pre-ordering**，若允许则在守恒方程中加入期前到货项。
2. 若不允许，计算"零库存起步 + 提前期约束"下的**理论最小缺货成本**作为合理性下界，确认求解结果与下界差距在合理范围内。
3. 不得为消除此结构性缺货而放宽提前期约束或虚构初始库存。

### 坑 5:求解精度不足导致近优解停滞

**现象**：所有约束验证通过，但评分略低于 1.0（如 0.998–0.999）。

**根本原因**：求解器默认 MIP gap（如 1e-3 或 1e-4）可能在大规模问题中留下可改善的余量；或需求份额拆分产生浮点截断，引入微小不可行间隙。

**正确做法**：

1. 显式设置更严格的 gap 容差，如 `mip_gap=1e-5` 或 CBC 的 `fracGap=1e-6`。
2. 对多个随机种子或求解器重启进行尝试，选最优incumbent。
3. 检查需求拆分是否产生整洁的整数或有限小数，浮点截断引起的微小差异可通过对齐取整解决。
4. 确认缺货惩罚在目标函数中被充分最小化——在容量和采购限制允许的情况下，不应存在可避免的缺货。

## 子族 A 专属坑(多 DC 独立)

### 坑 A1:替代方向反了

通常是 **Premium 替代 Basic**(高替低)。
错误建模：`sub_in[basic, t]` 来自 `sub_out[basic, t]`（自己替自己——荒唐但常见）
正确：`sub_in[basic, t] == sub_out[premium, t]`，且 `sub_out[premium, t] <= inv[premium, t]`。

**Hub-Spoke 额外检查**：若问题同时含 Hub-Spoke 结构，替代的 `sub_in / sub_out` 项必须同时出现在**中央仓**和**地区仓**的守恒方程中——只在其中一层加，会产生虚空库存。

**替代变量末期检查**：在最后若干期，若高价品库存充足而需求低，求解器可能因替代约束过于宽松而过度替代，拉高持仓成本。验证时应检查末期 `sub_out` 是否存在非必要的大量替代。

### 坑 A2:保质期约束太松或太紧

- 近似法 `inv[t] <= sum(demand[t..t+shelf-1])` 容易过紧（不允许任何安全库存）
- 精确批次法 `batch[..., t_arr, t]` 变量数会爆（数百 → 数千）
- 折中：用近似法 + 在目标里加大损耗惩罚，让求解器自然规避囤积

**短保质期场景（shelf_life - lead_time ≤ 2 期）额外注意**：

- 该近似约束可能在低需求节点（需求份额较小的 DC）中过紧，迫使安全库存为零、引发可避免缺货。
  可放宽为 `inv[dc,sku,t] <= sum(demand[dc,sku,t..t+shelf_life]) * 1.05`（仅对短保 SKU）。
- 约束必须**按 DC 分别施加**，而非全网汇总——地区仓需求与中央仓独立，汇总约束会掩盖局部过剩。
- **"零废弃"出现在短保 SKU 的验证结果里是危险信号**，需检查约束是否失效或过紧，而非视为优化成功（见下方"零废弃 = 危险信号"说明）。

#### ⚠️ "零废弃 = 危险信号"主动触发规则

若验证结果显示**所有 DC、所有短保 SKU 废弃均为零**，必须区分以下两种情况：

| 情况 | 含义 | 处理 |
|------|------|------|
| 保质期约束过紧，需求自然消耗不完库存 | 约束掩盖了真实积压，可能同时掩盖容量违反 | 检查约束是否实际生效，放宽后重新求解 |
| 需求自然消耗所有库存，约束不活跃 | 正常情况 | 无需处理 |

区分方法：对比"无保质期约束时的最优解"与"有保质期约束时的最优解"——若两者库存剖面完全相同，则约束不活跃（正常）；若有差异但废弃仍为零，需进一步检查。

即使评分接近满分，也应执行此检查，不得跳过。

### 坑 A3:产能"全网合计"误写为"每 DC"

问题描述写"全网所有 DC 同 SKU 总采购 ≤ X 件/周"。
错：`sum_t order[dc, sku, t] <= X`（按 DC 限）
对：`sum_dc order[dc, sku, t] <= X`（每周按 SKU 跨 DC 求和）

**建模前强制注释块**（必须在实现前写出）：

```python
# ============================================================
# 产能约束形式（强制在实现前写出）
# sum over ALL DCs of order[dc, sku, t] <= supplier_capacity[sku]
# for each sku, for each t
# 注意：是跨 DC 求和，不是按 DC 分别约束
# ============================================================
```

**产能约束符号**：使用 `<=` 而非 `<`。验证时容差设为 `1e-4`，不得用 `1.0`——精度过松会放过真实违反。

**强制后验检查**：求解后必须重新计算 `sum_dc order[dc,sku,t]` 对每个 `(sku, t)`，断言结果 `<= capacity[sku] + 1e-4`，未通过则禁止提交。

### 坑 A4:DC 容量按"件数"还是"加权占用"

冷藏 / 体积场景需用 `weight[sku]`（不同 SKU 占空间不同）。
错：`sum_sku inv[dc, sku, t] <= cap[dc]`
对：`sum_sku inv[dc, sku, t] * weight[sku] <= cap[dc]`

**建模前强制步骤**：

1. 在代码注释中逐字写出加权容量约束形式，标明每类 SKU 的权重值。
2. 打印 / 断言权重字典包含**全部 SKU** 的正确值，不得有遗漏或默认值为 1.0 的错误填充。
3. 对**至少一个 DC、一个时期**，将约束行展开为符号形式（如 `w1*inv[DC1,SKU_A,1] + w2*inv[DC1,SKU_B,1] <= cap`），目视核查权重是否正确。
4. 写出后再实现，防止字典遗漏或数值填错。

**容量约束覆盖率检查**：实现后，统计实际添加的容量约束行数，断言等于 `len(DCs) × len(periods)`，确认无 DC 被遗漏（尤其是地区仓）。

```python
# 强制断言：容量约束覆盖所有 DC 和所有期
assert capacity_constraint_count == len(DCs) * len(periods), \
    f"容量约束数量 {capacity_constraint_count} ≠ 预期 {len(DCs) * len(periods)}，有 DC 被遗漏"
```

### ⚠️ 坑 A5：批次追踪 MIP + 外部仿真 = 容量约束隐性违反（最高优先级禁止项）

**这是最高优先级的禁止项。违反此条必定导致评分为零。**

**现象**：求解器报 Optimal，自验"零容量违反"，最终评分 0.0，评估器报大量容量超限。
另一诊断信号：自报持仓成本 X，评估器计算出的持仓成本 Y ≈ 1.5–2× X，
说明外部仿真比 MIP 保留了更多库存，容量违反在所难免。

**根本原因**：

批次追踪 MIP 引入了连续流变量（形如 `flow[dc, sku, batch_index, t]`），求解器用**最优流分配**（把某期消耗量拆给多个批次）满足容量约束——但这套分配是"数学最优"，物理上**不遵循 FIFO**。随后用 FIFO 仿真重放同一份下单计划时，批次消耗顺序不同，库存剖面也不同，容量约束就会被突破。

而且自验函数通常调用 MIP 内部的 `inv` 变量值（已按 MIP 最优分配），不调用外部仿真的结果，所以自验会通过但评估器会失败。

**强制规则（硬性禁止，无例外）**：

> **NEVER** 使用批次追踪 MIP（即带批次索引流变量的模型）。
> **ALWAYS** 使用聚合库存模型（单一 `inv[dc,sku,t]` 变量，不拆批次）。
> 若代码中出现任何形如 `flow[..., batch_index, ...]` 的变量，**必须重写整个模型**，不得仅删除该变量而保留其他批次相关结构。

**模型架构门控（在写任何变量前执行）**：

```python
# ============================================================
# 模型架构门控（强制）
# 本模型使用聚合库存 inv[dc, sku, t]
# 禁止引入任何形如 flow[dc, sku, batch_index, t] 或等价批次追踪变量
# 禁止引入任何以"批次到达时间"为索引的多维流变量
# 聚合库存模型中，MIP 约束的 inv[dc,sku,t] 与任何外部仿真使用的库存值完全相同
# （单一聚合量，没有"流分配"歧义），约束保证有效
# ============
