## 输出要求

使用 Edit 工具把一份可独立阅读的 Markdown 演化总结写入：

`${worktree_result_path}`

不要输出 JSON，不要写 task_id、run_id、绝对路径或系统状态字段。总结应覆盖以下内容，标题可以自然调整：

- 演化摘要：在文档开头使用 `## 演化摘要`，用 1--3 句话概括这次演化最重要的路线、发现和最终结论；这段文字会进入跨任务索引，必须脱离具体 Run 标识也能帮助后续 Agent 判断是否值得深入阅读；

- 演化路线：尝试了什么，方案如何 refine、switch 或 fuse；
- 关键发现：演化中确认的机制、规律和重要观察；
- 出乎意料的发现：与初始假设不一致或反直觉的结果；
- 最佳方法：核心机制、优势、代价及其胜出的公开证据；
- When to use：适用的数据特征、任务条件、资源条件和评测条件；
- When not to use：不适用条件和可能造成 negative transfer 的情形；
- 失败方向：方法失败与实现、资源、evaluator 故障分开说明；
- 证据与置信度：区分正式评测结论、有限观察和未验证假设。

`When to use` / `When not to use` 是这份总结**唯一会被其他任务真正使用**的部分——
后续 Agent 读它是为了判断「这条经验适不适用于我手上这道题」。因此：

- 写清适用条件所依赖的**数据特征和评测条件**，而不是复述方法名称；
- 分数区间不可迁移，不要把「本任务拿到 +0.13」写成对新任务的收益预期；
- 工程性结论（如「大归档流式解压」「分块常内存设计」）往往比算法结论更可迁移，
  但必须标明它是工程结论；
- 明确写出哪些做法**不应**迁移，以及为什么——这一节为空说明复盘没做完。

Markdown 必须基于你实际读到的公开事实；没有证据的章节应明确写"未确认"，不要补造内容。除该 Markdown 文件外不要写其他文件。写完后自然退出。
