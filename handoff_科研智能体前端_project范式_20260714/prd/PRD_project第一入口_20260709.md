# PRD：Project 作为第一入口

> 版本：v1.0（2026-07-12）
> 定位：本产品的**总纲/产品定义**。界面呈现细节见配套《前端PRD_信息架构_20260710》。
> 参考：OpenScience（project 绑工作目录、coding agent 本地执行）、ChatGPT Projects（项目共享+对话隔离）、Zotero（账号级文献库）。
> 写作原则：**每个决策带推理链路**（为什么这么做 / 为什么不那么做），便于评审质疑与回溯。
> **术语约定（与代码一致）**：「**临时对话**」= 发起散聊的入口/动作（落地页右上按钮）；「**未归档对话**」= 承接这些散聊的内置项目/容器（session 归属它）。下文出现「临时对话（未归档）」即指"点临时对话入口 → 会话落入未归档对话项目"。

---

## 1. 一句话

**把「Project」而非「一次对话」作为第一入口。** 用户进来先建/进一个研究项目；Project 里只有两样东西——**Workspace**（干活的文件）和 **Sessions**（多次对话）——外加账号级的**文献库**。用户几乎不用想"东西该加哪去"。

## 2. 为什么（问题）

科研 Agent 若以「一次对话」为单位，有三个硬伤：
- **上下文不复用**：每开新对话都要重新交代背景、重传文件。
- **成果留不住**：跑出的代码/数据/图散落在几百个对话里，几天后找不回。
- **协作与复现难**：换机器、换人，接不上进展。

**根因**：科研是**长程、多轮、需积累**的活动，天然是「项目」尺度，不是「对话」尺度。所以第一入口必须是 Project。

## 3. 核心结构：Project = Workspace + Sessions

```
账号级
├── 📚 文献库（Zotero 式，跨 project 共享）
├── 💬 临时对话（未归档）  不属于任何 project 的轻量散聊，可「移入项目」升级
└── 项目 Project[]（第一入口）
     ├── 🗂 Workspace   本项目唯一的文件存储（真实目录树，agent 读写/跑代码）
     │     ├─ [原始输入] 用户 pin 的源文件/数据集（受保护，改前授权）
     │     └─ [工作文件/产物] agent 读写、生成的一切
     └── 💬 Sessions[]  本项目下的多次对话（历史隔离，都对着同一 Workspace；session 属于 project，非全局）
```

**给用户的一句话心智**：
- 要**处理**的文件 → 进 Workspace（agent 在这跑）
- 要**引用**的论文 → 进文献库（读它、引它）
- 没有第三个仓库要记。

## 4. 关键决策与推理链路

> 这是本 PRD 的核心。每条：结论 + 为什么这么做 + 为什么不那么做。

### D1. 区分「工作态」与「资产态」（整个模型的地基）
- **工作态** = Workspace 里的代码/数据/中间产物，依赖 project 上下文，拿出去没意义 → **锁在 project**。
- **资产态** = 有独立价值、想复用的东西（数据集/模型/关键图/**文献**）→ **可跨 project 流动**。
- **为什么**：之前把两者混谈，才反复纠结"加哪去"。分开后所有归属问题都用这条判据解。

### D2. Workspace = 本项目唯一的文件存储；能跑代码、有目录结构
- **为什么保留目录树**：科研 workspace 是代码+数据+实验，有依赖（`train.py` import `utils.py`、读 `data/`）。**不能像 ChatGPT 那样铺平**——铺平了 agent 就跑不了。
- **能力假设**：每个 project 有一块**持久、可跑代码、有目录结构**的 workspace。
- **为什么存储架构不进 PRD**：底层是云沙箱常驻还是按需拉临时环境，是后端实现，用户无感知，不影响任何产品逻辑。别让它卡住设计。（注：本产品是 Web 形态，workspace 在云端，非本地 app。）

### D3. 上传物与产物区分 = 只做「原始输入」一个不对称标记
- **结论**：不做"我上传的 vs AI 生成的"对称二分；只 pin「原始输入」（用户源文件，受保护，agent 改前授权）。
- **为什么**：价值不对称。"找我传的原始数据"是真需求（怕被中间产物淹没、被改坏）；"找 AI 生成的"几乎没人主动筛（用户在对话里就看到了）。做对称标签是浪费。
- **为什么保留原始输入**：科研里"原始数据神圣不可改"是刚需。（此项已在现有前端实现。）

### D4. 取消「知识库」独立实体
- **结论**：不再有并列的"知识库"仓库；"给 AI 参考的文档"就是 Workspace 里的文件。
- **为什么**：多一个并列概念 = 多一份"加哪去"的纠结。参考文档和工作文件本质都是文件。
- **为什么不用"读/写"切分**：曾想过知识库=读、workspace=写。但"读/写"是**系统实现视角，不是用户心智**——用户不会想"这文件给 AI 读还是写"，且数据集天然又读又写。维度作废。
- **唯一例外**：文献（见 D5）。

### D5. 文献单独一个轻库，账号级（Zotero 模型）
- **结论**：文献库是**账号级**的第二块存储，不属于单个 project；project 只记"引用了其中哪几篇"。
- **为什么单独**（理由不是读/写，是它是「另一物种」）：
  1. 引用对象，不是工作文件（你不 edit 一篇 arxiv 论文，你读它/引它/cite 它）。
  2. 天然跨 project（同一篇经典论文，风阻和润滑油项目都可能引）。
  3. 检索维度不同（文件按名/类型/时间；文献按作者/年份/DOI/语义）。
- **为什么账号级而非 project 内**：本产品文献是核心（Deep Research 型、大量引用、产出带引用报告），跨 project 复用文献高频。

### D6. 文件 vs 文献条目是两回事（解决"用户传的论文 vs AI 找的论文"矛盾）
- **矛盾**：用户上传的论文在 workspace（打了原始输入）；AI 检索的论文也落 workspace——那文献到底进 workspace 还是文献库？
- **结论**：分清「文件」和「文献条目」。
  - 论文的 **PDF 文件** 可在 workspace（agent 要读、cite）。
  - 它的 **文献条目**（作者/年份/DOI/摘要/引用片段）进**文献库**。
  - 两者指向同一篇；文献库里能看到"它在哪些 project 被引用"。
- **于是**：用户传的、AI 找的，在文献库里统一成"文献条目"，平等作为可引用文献存在。

### D7. 跨 project 复用产物 = 显式、低频；MVP 不做
- **结论**：产物默认待在诞生的 project（零决策）；跨 project 复用是显式的"复制/存为资产"动作，MVP 先不做，架构留口不焊死。
- **为什么默认不流动**：99% 情况产物就该留原地。若每次产出都问"加到哪个 project"，就又回到"加哪去"的混乱。
- **为什么低频**：用户真想带走的几乎都是资产态（数据集/模型/图），不是随便一个 log。
- **为什么 MVP 不做**：为低频场景提前增复杂度不划算，等真实反馈再做。

### D8. Agent 编辑 Workspace 需申请授权
- **结论**：agent 写/改/删 workspace 文件前向用户申请，粒度：本次 / 本对话 / 本项目长期；危险操作（删大量文件、改「原始输入」）**始终强确认**，不受长期授权覆盖。
- **为什么**：workspace 有用户真实数据，尤其 Web 形态、云端执行，安全与信任是底线。授权分级避免每步都打扰。

### D9. 暂不做：配置 / 研究图 / 项目系统提示词
- **结论**：模型/key/工具配置、结构化研究图(provenance)、项目级 system prompt——**移到待办**，本期不做。
- **为什么**：第一入口成立的最小闭环是"project = 能被 agent 反复读写的共享 workspace + 多对话"。这三样是增强项，不影响入口成立，先放待办。

### D10. 保留「临时对话（New Chat）」轻入口，与项目并存
- **结论**：`project first` ≠ 凡事必须先建项目。保留一个**弱化的临时对话入口**，承接不值得建项目的快速散聊。
- **场景/链路**：概念快速澄清、看段代码、临时查个东西、探索期"先聊两句试试"——占日常大多数（ChatGPT 已验证）。逼用户"先建项目才能聊"会赶走人。
- **临时对话特性**：不属于任何 project、**不建 workspace**；可丢弃，或对有价值的散聊「移入项目」升级。
- **为什么不砍**：project 是低频重容器，散聊是高频轻需求，二者是不同链路，缺一不可。

### D11. 导航三层 + session 归属 project（不照抄 OpenScience 整页 grid）
- **结论**：
  - **顶层**：项目（已有项目 + 新建项目）**常驻**；另有弱化的「临时对话（未归档）」槽。
  - **项目内**：左栏 = 该项目的 sessions + New session。**session 属于 project，非全局列表**（切项目换一批）。
  - **临时对话**：挂顶层，通过「项目切换器下拉底部的未归档槽」+「项目首页的轻入口」两处可达。
- **为什么 session 归 project**：这正是"项目内多会话共享同一 workspace"的落地；全局 session 列表会让"哪个会话属于哪个研究"混乱。
- **为什么不照抄 OpenScience 整页 grid**：OpenScience 每次都用整页项目网格拦一道，重。伐谋改成**常驻紧凑切换器**（点▾才展开全部/进项目首页），老用户不被拦。

## 4b. 界面落地形态（基于伐谋现状 + 参考 OpenScience）

> 现状（伐谋）：一进来即主 chat，无 project 概念；左栏含 知识库/资产/MoonLog。
> 参考（OpenScience）：整页项目卡片首页 + 固化 new project 按钮 + 进项目后左栏是该项目 sessions（图13）。
> 取其"project first + 新建固化 + session 归项目"，弃其"每次整页 grid 拦截 + 纯文件夹路径感"，做成伐谋墨绿风。

**左栏结构（改造后）**：
```
伐  百度伐谋
[ 当前项目：GNN风阻 ▾ ]        ← 项目切换器（常驻）；点▾ = 全部项目 / 进项目首页 / 底部“临时对话”槽
[ ＋ 新建项目 ]                ← 固化、醒目（重入口）
────────────────
本项目会话：                    ← session 属于本 project
  · 复现GNN论文…
  · 调研RL润滑油…
[ ＋ 新对话 ]                  ← 弱化、小（项目内=新建本项目会话）
────────────────
📚 文献库(账号级)   🌙 MoonLog
（✗ 资产：砍掉；✗ 知识库并列概念：并入 workspace，文献走文献库）
```

**默认第一入口**：
- **记住上次打开的项目**，直接进其工作界面（老用户不被拦）。
- **首次 / 无项目** → **项目首页**（伐谋风卡片网格：项目名 / 最近活动 / 会话数，非纯文件夹路径）引导建第一个项目。

**两个"新建"入口的定位**：
| 入口 | 权重 | 落点 |
| --- | --- | --- |
| ＋ 新建项目 | 固化、醒目 | 新建一个 project（重，带 workspace） |
| ＋ 新对话 | 弱化、小、隐含 | 项目内→本项目新会话；无项目上下文→临时对话（未归档） |

**临时对话（未归档）落点**：切换器下拉底部的弱化槽 + 项目首页轻入口；选中它 → 左栏为未归档对话历史，可对某条「移入项目」；在具体项目工作界面内不显示（避免混淆）。

## 5. 核心流程

```
① 建/进项目 → 指定/生成一块 Workspace（可选：上传初始文件夹/数据，pin 为原始输入）
② 在项目内开对话 → 自动带上 workspace 现状与项目上下文，直接下任务
③ Agent 执行 → 需写文件时申请授权；产出自动落 Workspace（零决策）
④ 多对话并行/迭代 → 聊天历史各自隔离，成果都汇入同一 Workspace
⑤ 用到文献 → 上传或 AI 检索得到的论文成为「文献条目」进文献库，可在正文引用（含引用片段）
⑥ 回看/复现/换环境 → 带着 Workspace + 项目即可接续
```

## 6. 功能需求

### P0（第一入口最小闭环）
1. **项目 CRUD**：创建/进入/列出/删除；创建时绑定一块 workspace。「＋新建项目」固化入口。
2. **导航：项目切换器 + session 归项目**：左栏常驻项目切换器（当前项目▾）；进项目后左栏为该项目 sessions + New session；默认进上次项目，首次/无项目进项目首页引导。
3. **临时对话（New Chat）轻入口**：弱化的「＋新对话」；无项目上下文时落"临时对话（未归档）"，可「移入项目」升级（D10/D11）。
4. **Workspace 读写执行**：agent 能在项目 workspace 内读/写/跑代码，文件有目录结构。
5. **原始输入 pin + 改动授权**：用户源文件可标记受保护；agent 写操作按 D8 分级授权、危险操作强确认。
6. **项目内多对话共享 workspace**：项目内新建会话继承项目上下文、共享同一 workspace；聊天历史隔离。
7. **文献库（账号级）+ 引用片段**：文献条目（作者/年份/DOI/摘要）跨 project；正文引用可追溯到片段（前端已落地）。
8. **左栏精简**：砍掉「资产」；「知识库」并列概念取消（并入 workspace）；文献走「文献库」；MoonLog 保留。

### P1
9. **Workspace 迁移/复现**：项目状态可导出/迁移，换环境接续。
10. **文献库独立页**：Zotero 式，按作者/年份/DOI/语义检索，看"被哪些 project 引用"。
11. **项目首页**：伐谋风卡片网格（项目名/最近活动/会话数）+ 临时对话轻入口；「查看全部项目」可达。
12. **Workspace 人视图**：目录树 ⇄ 铺平资料库切换 + 文件即入口（选中文件开新对话，借鉴 ChatGPT）。

### 待办（本期不做，后续评估）
- 跨 project 复用产物（D7，架构留口）。
- 项目配置 / 研究图 provenance / 项目系统提示词（D9）。
- 存储架构选型（D2，工程侧）、多人协作、项目模板。

## 7. 边界（非目标）
- 不做通用聊天入口；散聊由"临时对话"承接，不强制建项目。
- Workspace 与文献之外**不再有第三个仓库**（砍掉知识库、资产）。
- Workspace 默认**不跨 project 共享**，避免文件污染与数据泄漏。
- Agent 组织自主 ≠ 无约束：始终受授权门控，危险操作强确认。

## 8. 衡量指标
- **复用率**：项目内二次对话占比（越高 = 项目沉淀被用起来）。
- **长程价值**：单项目平均对话数、workspace 文件增长曲线、项目存活周期。
- **认知负担**：用户"加东西"时的犹豫/撤销率（是否真的不用想"加哪去"）。
- **信任**：授权申请→授予转化率、撤回率；引用片段展开率。

### 附：一句话竞品对照
- **ChatGPT Projects**：项目共享文件+指令、对话隔离——成熟范式，但研究状态只到"文件+记忆片段"。
- **OpenScience**：project 绑工作目录 + coding agent 本地执行——workspace 能跑代码的范式来源。
- **Zotero**：账号级文献库、每处只记引用——文献库直接采用此模型。
- **差异化机会**：多数产品的"项目"只到知识+配置层；把"能跑代码的 workspace + 可追溯引用"做进项目层，是当前空档。
