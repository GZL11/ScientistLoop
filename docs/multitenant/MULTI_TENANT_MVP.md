# Famou 多租户 Web 服务 — MVP 评估

> 目标：本机部署一个稳定服务，**多个外部用户各自打开网页链接使用**，彼此**不共用工作目录、不共用 opencode db、不串会话**。
> 约束（已定）：**共用平台方（你）的模型 key**，但**会话/产物数据严格隔离**；身份方案待定（本文档对比两种）。
>
> 结论先行：**能做到，且 MVP 改动面不大**——因为隔离所需的两个旋钮（`XDG_DATA_HOME`、进程 cwd）代码里已经存在，缺的是它们之上的
> **身份 + 实例分发 + 路由 + 生命周期**这一层网关。本文档评估「最小可行多租户」的形态、改动量、风险。

---

## 一、为什么当前不行（一句话根因）

opencode 是**单用户工具**：一台机器 = 一个人 = 一个全局 `~/.local/share/opencode/opencode.db`（当前已 287MB）。
现在 `famou web` 起的是**一个共享后端实例**（`127.0.0.1:4097`），所有访问者读写**同一个 db、同一个 research-runs 目录**
→ 串会话、抢产物。这不是 bug，是「把单人工具当多人服务用」的架构错配。

## 二、好消息：隔离旋钮已存在（无需从零发明）

| 隔离维度 | 机制（已在代码里） | 位置 |
|---|---|---|
| 会话 / opencode db | `_opencode_data_dir()` 读 **`XDG_DATA_HOME`** → 每人一套即物理隔离 db | `web.py:137` |
| 研究产物 research-runs | 后端 **cwd 决定落点**（launcher/web 都「不改 cwd」）→ 每人一个 cwd 即隔离 | `web.py:20`、`launcher.py:18` |
| 端口 | `serve_web(web_port, oc_port, host, auto_port)` 已支持指定/自动找端口 | `web.py:184` |
| env 透传 | 起 `opencode serve` 时整个 `env` 透传 → 可注入 per-user `XDG_DATA_HOME`/cwd | `web.py:334` |

也就是说：**「一个用户 = 一套 XDG_DATA_HOME + 一个 cwd + 一对端口 + 一个 opencode serve 实例」** 这个隔离单元，
底层已经拼得起来。MVP 的工作 = 在它上面加一个**网关**，负责「谁来了 → 分配/复用他的隔离单元 → 把他的网页请求路由过去」。

## 三、MVP 形态（路线 A：轻量多实例 + 网关）

```
                 ┌─────────────────────────────────────────────┐
   浏览器 ──────►│  Gateway（新增，唯一对外 0.0.0.0:PORT）        │
  (带登录态)     │   ① 鉴权：cookie/token → user_id              │
                 │   ② 实例表：user_id → {oc_port, web_port,     │
                 │              XDG_DATA_HOME, cwd, pid, 最后活跃} │
                 │   ③ 按需拉起/复用该 user 的 famou 实例         │
                 │   ④ 反向代理：把请求转到该 user 的 web_port    │
                 │   ⑤ 闲置回收 / 崩溃重启 / 并发上限             │
                 └───────┬───────────────┬───────────────────────┘
                         │               │
        ┌────────────────▼───┐   ┌───────▼────────────────┐
        │ user A 的隔离单元    │   │ user B 的隔离单元        │   … 每人一套
        │ XDG=/data/users/A   │   │ XDG=/data/users/B       │
        │ cwd=/work/A         │   │ cwd=/work/B             │
        │ opencode serve :51xx│   │ opencode serve :52xx    │   ← 全绑 127.0.0.1
        │ famou web    :41xx  │   │ famou web    :42xx      │      （只网关对外）
        │ → 独立 opencode.db  │   │ → 独立 opencode.db      │
        │ → 独立 research-runs│   │ → 独立 research-runs    │
        └─────────────────────┘   └─────────────────────────┘
```

**关键设计点：**
- 所有 famou/opencode 实例**仍绑 127.0.0.1**（沿用现状，最安全）；**只有网关**绑 `0.0.0.0` 对外。外部用户永远打的是网关。
- 网关是**唯一新增的核心组件**；每个隔离单元几乎**直接复用现有 `serve_web()`**，只是换 `XDG_DATA_HOME` + cwd + 端口。
- 数据布局：`/srv/famou/users/<user_id>/{xdg/, work/}`，一人一棵子树，天然隔离，也方便配额/清理/备份。

## 四、凭证处理（按你的决定：共用你的 key，隔离数据）

- 模型 key 继续走**平台级 env**（`ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN` 等），由网关注入到每个实例的 env——
  **用户看不到、拿不到 key**（他们只经网页说话，key 在服务端进程 env 里，不下发到浏览器）。
- ⚠️ 但「共用 key」= **用户共享你的额度**。MVP 必须配套**每用户配额/限流**（见 §六），否则一个人可烧光你的额度或占满 GPU。
- 你反复强调的红线在此架构下**默认满足**：key 从不进 db、不进 research-runs、不下发前端；只在服务端进程 env。

## 五、身份方案对比（你要的两选一材料）

| 维度 | 方案①：接现有 SSO/OAuth | 方案②：自建轻量账号（用户名/口令 或 邀请 token） |
|---|---|---|
| 上手速度 | 中（要接公司 IdP、配回调） | 快（一张 users 表 + 登录页 + session cookie） |
| 安全 | 高（密码/MFA 由 IdP 兜底，不自存密码） | 需自己扛：口令哈希、session 防护、暴力破解限流 |
| 合规/审计 | 好（统一登录留痕、离职即失效） | 要自己做用户增删、禁用、审计 |
| 外部用户（非本公司）能否用 | 取决于 IdP 是否对外 | 容易（发邀请 token 即可） |
| 运维成本 | 依赖 IdP 可用性 | 全在自己手里，但安全责任也全在自己 |
| **建议** | **若用户都是内网员工 → 选①**（最省心最合规） | **若有外部/临时用户、或没有可接的 IdP → 选②**（先 token 邀请制起步） |

> MVP 建议：**先做②的最小版（邀请 token → 换取 session cookie）**把整条多租户链路跑通，身份层留成**可插拔接口**，
> 之后接①只是替换「验证凭证 → user_id」这一个函数。不要一上来卡在 SSO 对接上。

## 六、要补的横切能力（"稳定"二字的成本大头）

| 能力 | 不做的后果 | MVP 最小实现 |
|---|---|---|
| 实例生命周期 | 实例越堆越多 / 崩了不起 | 按需拉起 + 闲置 N 分钟回收 + 崩溃重启 + 全局实例数上限 |
| 资源配额 | 一个人跑训练拖垮所有人 | 每 user：并发实验数上限、磁盘配额、（可选）GPU 名额；`.famou_jobs` 也要 per-user |
| 并发/限流 | 共用 key 被烧爆 | 网关级每 user QPS/额度限流 |
| 崩溃隔离 | 一个实例 OOM 连累整机 | 至少 cgroup/ulimit；要更硬就上路线 B 容器 |
| 数据清理/备份 | 磁盘写满 / 丢数据 | per-user 子树定期清理 + 备份策略 |

## 七、改动面盘点（MVP，路线 A）

**新增（核心）：**
- `gateway`（新组件，约几百行）：鉴权中间件 + 实例注册表 + 反代 + 生命周期。可 Python(aiohttp/starlette) 或复用现有 Node server.mjs 思路扩展。
- 身份层最小实现（②）：users/token 存储 + 登录端点 + session 校验。
- per-user 目录布局与分配逻辑。

**改造（小）：**
- `web.py`：把 `serve_web()` 参数化到「传入 XDG_DATA_HOME、cwd、端口」即可被网关按 user 调用（现在已接近，主要是把 env/cwd 显式提上来）。
- `.famou_jobs` 根（`ARC_JOBS_DIR`，heartbeat/async_runner 已支持 env 覆盖）→ 每 user 一个，避免异步实验 job 混池。

**基本不动：**
- opencode 本体、研究流程、skill/tool/plugin、评测套件。多租户是**外挂一层**，不侵入研究内核。

## 八、明确不做 / 边界

- 不改 opencode 让它原生多用户（= 路线 C，重做后端，不在 MVP）。
- 不上 k8s（= 路线 B，等 MVP 验证规模后再谈）。
- 不让用户自带 key（本次你已定共用你的 key）。
- 不做前端大改；登录页可以是最简单一页。

## 九、风险与未决

1. **共用 key 的额度/滥用**：MVP 必须带每用户限流，否则第一天就可能被烧爆——这是最高优先级配套项。
2. **opencode db 单文件锁**：每人独立 db 后无跨用户锁问题；但要确认 opencode 允许同机多实例（不同 XDG + 不同端口）并行——**需一个小实测验证**（起两套 XDG/端口，确认互不串、db 各写各的）。
3. **GPU 争用**：多人同时跑实验，`.famou_jobs`/GPU 需要调度，否则互相抢卡。MVP 可先「实验排队 + 每人并发上限」兜底。
4. **磁盘增长**：research-runs + db 会持续变大（现单 db 已 287MB），per-user 配额与清理不能省。

## 十、建议的推进顺序（每步可独立验证，不一次吃成胖子）

1. **可行性实测**（半天）：手工起两套 `XDG_DATA_HOME`+cwd+端口 的 famou 实例，确认**会话/db/产物完全不串**。这是整个方案的地基假设，先证实。
2. **隔离单元函数化**（小）：把「按 user 参数起一套隔离实例」封装成一个可调用单元（复用 `serve_web`）。
3. **最小网关 + token 身份**（中）：登录 → user_id → 拉起/复用实例 → 反代。跑通「两个用户各自网页、互不可见」。
4. **横切兜底**（中）：闲置回收、每 user 并发/额度限流、per-user `.famou_jobs`。
5. **对外暴露 + 加固**（小-中）：网关绑 0.0.0.0 + 前置 TLS/nginx；压测；再放量。
6. （可选）身份层换成 SSO；（可选）规模上来后迁路线 B 容器化。

> 第 1 步是「go/no-go」关口——只要同机多实例隔离实测通过，后面都是工程量问题，无架构级未知。
