# Agent View 架构设计

Agent 在一次研究 run 里能看到的全部东西，只有两样：**一个索引**和**一批方案目录**。本文定义这两样的结构、地址规则和字段集。

宿主留存（审计、复现、计费）是另一套结构，与本文不共用 schema，见 [HOST_RETENTION_CN.md](HOST_RETENTION_CN.md)。

## 1. 形状

```
expbank/
  INDEX.md      唯一索引：图结构 + 每个方案的一句话和分数
  0001/         一个方案的全部东西
  0002/
  ...
```

索引给方向，目录给细节。agent 读索引决定挖哪条，进目录拿代码和证据。中间没有第三层。

图不单独存。索引里的边由各方案 `record.json` 的 `parents` / `operator` 渲染而来，图结构没有独立的真值副本。

## 2. 身份

**一个方案一个号，`NNNN` 四位补零，在方案被提出时分配，终身不变。**

这个号是 agent 唯一需要知道的标识：索引每行开头是它，agent 填 `parents` 时写的是它，方案目录名也是它。

三条推论：

- 提出了但从未实现的方案，同样有号、有目录。它是合法的 `parents` 取值。
- 同一方案被实现多次（debug 重试），不产生新号；多次实现是这个号内部的事。
- 方案之间的父子关系是**方案→方案**。实现尝试之间不建立血缘。

## 3. 索引

> 落地文件名是 `expbank/GRAPH.md`（`EvolutionGraphStore.index_path`）。本文按角色
> 称它"索引"；上文形状图里的 `INDEX.md` 是同一样东西的旧名。

索引分两块：**路线**和**方案**。图结构由路线承载，方案区是扁平的，方案之间不互相指。agent 从头到尾读的都是线性列表，不做图遍历。

```
## 路线（根到叶的完整世系，按链上最好分从高到低；全部列出）

A  0001 → 0007 → 0012  最好 +0.0530  末端 0012 未实现
B  0001 → 0004 → 0019  最好 -0.0090  末端 0019 failed×1
C  0002                未出分        末端 0002 running

## 方案（按编号升序）

0001  频次基线          -0.0140   scored
      按 k-mer 频次直接投票，不做任何纠错。
      [idea_1789922344089_016c69b1]
0007  门控残差共识纠错  +0.0530   scored
      把 argmax 共识换成按覆盖度门控的监督残差纠错。
      [idea_1789922344091_bb2]
0012  覆盖度自适应阈值  未出分    未实现
      门控阈值不写死，按局部覆盖度分位数自适应。
      [idea_1789922344092_cc3]
0021  门控 + 加权融合   +0.0310   scored  ← 0007, 0004
      取 0007 的门控和 0004 的质量加权，两级串联。
      [idea_1789922344093_dd4]
```

**编号在提交时分配并落盘（`record.seq`），不在渲染期现算。** 渲染期算的号看似也稳定，
但任何改变排序的因素都会让它整体漂移一位——agent 上一回合记住的 0007 下一回合指向别人，
而这种错不报错，只会悄悄建错边。取"已用最大值 + 1"而不是"节点个数 + 1"：后者在任何一次
读取失败时都会撞上已经发出去的号。

**`parents` 里填 `NNNN` 或长 node_id 都收**，宿主统一解析成 node_id 再落盘——磁盘上
只有一种主键，`graph/<node_id>.json` 的文件名不受编号影响。解析不出来的原样保留，走
正常的"父节点不存在"校验，agent 在那里会收到合法编号清单。

### 3.1 路线

一条路线 = 从根方案到叶子的一条完整世系链。**全部列出，不截断、不排名截尾。**

| 字段 | 内容                                                |
| ---- | --------------------------------------------------- |
| 编号 | `A` / `B` / …，只供行内引用，不持久化          |
| 链   | `NNNN → NNNN → NNNN`，根在左                    |
| 分数 | 链上的最高分                                        |
| 说明 | 一句话：这条接着走是什么。宿主生成，不是 agent 写的 |

排序按链上最高分降序，没出分的沉底（不是当成 0 分插到中间）。最后那句说明就是"下一步挖哪个"——未实现方案自身没有分数，要不要做得看它所在链的成绩，这个叉乘由宿主算完，agent 读第一行即可。说明报的全是**末端**的状态（`未实现` / `running` / `failed×N` / `最后一跳 +0.xxxx`），因为这三种的处置方向完全不同。

多父方案（`cross` / `ensemble`）同时属于多条路线，在每条里都出现一次。

路线数有一个防呆上限（`ROUTE_LIMIT`，多父会让"根→叶"路径数按组合增长）。实测一个 run
路线数中位 7、最大 11，离上限很远；撞上时索引里**明写出来**，不静默少列几条。

### 3.2 方案

一个方案一行，按编号升序——顺序稳定，agent 多次读到的排列一致。

| 位置   | 内容                                                                     |
| ------ | ------------------------------------------------------------------------ |
| 行首   | `NNNN`，接着挖时填进 `parents` 的就是它                              |
| 标题   | 方案名                                                                   |
| 分数   | best_score；无分时留空，**不渲染成 0**                             |
| 结局   | `未实现`（一次都没做）/ `running`（做了还没出结果）/ `scored` / `failed×N` 等实测状态计数 |
| 行尾   | 仅多父方案（`cross` / `ensemble`）写 `← NNNN, NNNN`；单父的父由路线表达，行内不重复——那条边在路线里看得全，多父的边在任何一条路线里都只看得到一半 |
| 第二行 | `mechanism`，宿主截到 100 字，结尾 `…`                              |
| 第三行 | `[长 node_id]`，`graph/<id>.json` 的文件名，也是 grep 把手。不混进第一行——一串三十字的十六进制会把对齐好的列冲散 |

**长度由宿主控制，不由 agent 控制。** 标题和说明都在宿主侧截断，截断痕迹（`…`）必须可见，避免半句话被当成方案全貌。

方案目录地址由编号直接推出（`NNNN/`），不占一行。

### 3.3 校验

**在提交时校验，不在渲染时校验。** 只有提交那一刻 agent 还在现场，能收到报错并改；
渲染时再发现，方案已经写进去了，没人能修。

提交一个方案时必须带 `parents`，宿主检查：

| 检查         | 不通过时                    |
| ------------ | --------------------------- |
| `parents` 非空 | 报错退回，agent 重填        |
| 每个父是已存在的编号，或 `ROOT` | 报错退回，并告诉 agent 有哪些合法编号 |
| 算子与父的个数相符（见下表） | 报错退回，agent 重填      |

| 算子         | 父节点约束                              |
| ------------ | --------------------------------------- |
| `innovate` | 恰好`["ROOT"]`，是一条新路线的起点    |
| `exploit`  | 恰好 1 个已存在方案，接在其所在路线后面 |
| `cross`    | ≥2 个已存在方案，同时属于多条路线      |
| `ensemble` | ≥2 个已存在方案，同时属于多条路线      |

退回最多三次，仍非法就丢弃这条提案。**宿主不替 agent 把算子改成"最近的合法形态"**——改了它永远不知道自己填错，下次照错，而图上会多出一条它没打算建立的边，后来读图的人分不出哪些边是它真提的。丢一条提案，好过在图里留一条假边。

`cross` 和 `ensemble` 的父约束逐字相同，在图上也是同一种边。分开是因为**代价差一个数量级**：`cross` 拿走父的机制重新实现，要从头训；`ensemble` 直接加载父训好的权重，多数情况只需训一个很小的结合器。"这次要花多少时间"对 agent 是决定性的，混在一个词里它判断不了。

因为提交时已经挡住，渲染侧不再做准入判断：每个方案都必然挂在某条路线上，索引直接投影即可。

## 4. 方案目录

```
0007/
  SUMMARY.md     人读的一页：方案是什么、怎么实现的、结果、失败时错在哪
  record.json    结构化全量：方案本体 + 边 + 结局
  runs/1/        第 1 次实现
    code/          run.py 及其依赖
    evidence/      stdout / stderr 全量、评测产物
    weights/       方案自己存的权重（位置写在 instructions.md 里）
  runs/2/        第 2 次实现，结构相同
```

只提出、未实现的方案：目录里只有 `SUMMARY.md` 和 `record.json`，没有 `runs/`。它在索引里就是那个结局写着「未实现」、通常挂在某条路线末尾的编号。

**每次实现都留代码，无论结局。** 跑挂的、超时被掐的，`code/` 里同样是那次实现的 worktree 现状。下一次 debug 从这里起步，agent 也能看到一条路线的代码长什么样。

### 4.1 权重

`runs/<n>/weights/` 的路径由宿主指定，通过 `instructions.md` 告诉 agent，agent 把 ckpt 存在那里。

三条规矩：

- **能留就留。** 跑挂的那次也留——训到一半的 ckpt 正是判断"是代码坏了还是没学到东西"的材料。
- **跨方案可读。** 任何方案都能加载任何已存在方案的权重热启动，不限于自己的父。
  这是存权重的全部意义：`exploit` 继承的不只是代码思路，还有已经训出来的东西，
  子方案不必从头再训一遍。
- **不设紧的体积上限。** 尽量容纳；ckpt 的量级不构成约束。

权重是这个方案信息的一部分，和代码、证据同级，不是附属产物。

**索引里不标哪些方案有权重。** 权重不能单独使用——要加载它就得先看产出它的代码，
确认模型结构对得上。既然一定要开目录，索引上那一列就是多余的，标了反而让 agent
以为不用看细节。提 `ensemble` 的方案要自己翻候选父节点的目录。

宿主只在一处代劳：`ensemble`／`cross` 的方案进入实现队列时，请求里带上每个父节点的
`code` / `output` / `weights` 真实目录（`parent_artifacts`）。**只列实测存在的目录**——
路径是宿主查出来的，不是 agent 自报的；某个父没存权重，就没有那一项。

## 5. record.json 字段集

收录判据：**agent 读到它，会改变下一步提什么方案。** 不满足的字段不进 agent view。

| 字段                                       | 作用                                            |
| ------------------------------------------ | ----------------------------------------------- |
| `title` / `hypothesis` / `mechanism` | 方案是什么                                      |
| `rationale`                              | 为什么这么想——判断这条路线还有没有余地        |
| `implementation_plan` / `risks`        | 接着改时的起点和坑                              |
| `expected_return`                        | 它自己的预测；与实际分数对照就是校准信号        |
| `resource_request.expected_runtime_sec`  | 方案必须自己遵守 canonical 时限                 |
| `parents` / `operator`                 | 图结构本身                                      |
| `score` / `outcome` / `conclusion`   | 结果                                            |
| `failure`                                | 失败在哪：错误类别 + 日志路径。stderr 正文不内联，agent 要看自己去读 |
| `paths`                                  | 按需检索的入口                                  |
| `weights`                                | 这次实现存下了什么权重、在哪。别的方案据此决定要不要热启动 |

一个语义只存一份。方案的机制描述只有 `mechanism` 一个字段，索引里那句话是它的截断视图。

## 6. 结局词表

写在每次实现上，四个词：

| 词             | 含义             | agent 的处置             |
| -------------- | ---------------- | ------------------------ |
| `scored`     | 跑完了，有分     | 看分数决定接不接着挖     |
| `failed`     | 代码跑挂了       | 读 stderr，可以修        |
| `not_executed` | 跑不完，超时被掐 | 方案太重，要减配不是要修 |
| `running`    | 还在跑           | 别动                     |

（词表的真值在 `domain/status.py` 的 `LoopStatus.ExpBank`：`implementing` /
`implemented` / `not_executed` / `engineering_failed` / `evaluated` / `best` / `failed`。
索引里印的就是这些实测状态本身的计数，宿主不另做一层映射——多一层映射就多一处会漂的口径。）

`not_executed` 与 `failed` 必须分开：一个是"想法可能对但太贵"，一个是"代码有 bug"，处置方向相反。宿主侧对失败还有更细的分类，那些分类 agent 拿到也做不了什么，不进本视图。

方案级的 `best_score` 取其各次实现中的最高分；全部未出分时为空，**不渲染成 0**。

索引里只显示这一个最高分，不显示每次实现的分数序列——跑多次等价于"前几次失败了"，
次数本身不带方向性信息。要知道失败了几次、怎么失败的，进 `NNNN/runs/` 看。

## 7. 检索模型

两层，只有两层：

1. **索引** — 一个方案一句话。用来选方向。
2. **目录** — 全量。用来动手。

索引不承载细节，目录不承载导航。agent 不需要遍历目录树，方案目录名就是索引里的编号。

## 8. 边界

- **不去重。** 同一方案被重复提出仍按提案计数——提出一个新方案就是一次独立的探索决策。
- **不剪枝。** 低分方案照样留在索引里。
- **agent 只读。** 索引与方案目录由宿主渲染和写入，agent 不写回。
